    Lecture 7 — Regular Expressions

    A regex is a tiny language for a string's shape. With re.search you ask does this shape fit? — and once it fits, groups let you pull the pieces out. It replaces hand-written in/split/endswith checks that leak forever.

    What you'll be able to do

    • Use re.search(pattern, string) to test whether a pattern appears, reading its return as a match object (truthy) or None (falsy), and fold the test into one line with the walrus if matches := re.search(...):
    • Build a pattern from metacharacters — . any char, * 0+, + 1+, ? 0/1, {m,n} counts — written as a raw string r"..." so backslashes (\. literal dot, \w, \d, \s) reach the regex engine intact
    • Anchor with ^ (start) and $ (end) to require the whole string match, and combine character classes [...], negation [^...], ranges [a-z], alternation A|B, and groups (...) / non-capturing (?:...)
    • Match case-insensitively with the re.IGNORECASE flag, and extract captured text with .group(0) (whole match), .group(1) (first capture, 1-indexed), and .groups() (a tuple to unpack)
    • Clean and rewrite text with re.sub(pattern, repl, string) — stripping a varying prefix that a fixed .replace/.removeprefix can't handle — instead of patching in/split/endswith checks that leak forever

    re.search: does the pattern appear?

    Regex lives in the standard-library re module — import re (the same import from Lecture 4). The one function you'll use most is re.search(pattern, string): it hunts for pattern inside string and returns a match object if it finds one, or None if it doesn't. A match object is truthy and None is falsy (the truthy/falsy idea these notes added in Lecture 1 — the same idea behind that bare "Sun" that always fired), so you drop the call straight into an if. Here the pattern is just the literal "@". Predict the result before you Run.

    Live — re.search returns a match object (truthy) or None (falsy). The literal "@" just asks: is there an @ anywhere? Predict first.

    It found the @, so the match object is truthy and we print Valid. Two things to carry forward. First, the pattern comes first, the string second — re.search(pattern, string), easy to flip by accident. Second, that literal "@" is the floor: from here on we make the pattern describe a shape, not just a character, by adding metacharacters.

    Mental model — a pattern is a SHAPE, not a list of letters
    Plain text = literal: must appear exactly
    re.search("cat", "the cat sat")
    Every character stands for itself. This finds the three letters c, a, t somewhere in the text — here, inside the cat sat. No machinery, no surprises. This is the "@" search you just ran.
    search slides — it hunts ANYWHERE
    re.search("cat", "a category")  # FOUND
    The stencil slides along the text until it fits. So "cat" is happily found inside "a category" — re.search answers 'does this appear somewhere?', not 'is the whole string this?'. Pinning it to the whole string takes anchors — coming up in a few sections.

    Metacharacters, set 1: . and +

    Here is the first machinery. Each one is a quantity or a wildcard, not a literal:

    • . — any single character (except a newline)
    • + — the thing before it, 1 or more times

    So .+@.+ reads 'one-or-more of anything, then a literal @, then one-or-more of anything' — something must sit on both sides of the @. This is your first real shape. Predict: does "malan@harvard.edu" match, and would a bare "@" (nothing on either side) match?

    Live — .+@.+ requires at least one char on each side of the @. Try email = "@" and email = "a@b" to feel the +. Predict first.

    Now feel the stencil slide. Because re.search looks anywhere, that same shape .+@.+ is found inside a whole sentence — there's junk before and after the email, but the shape still fits somewhere in the middle. Predict: does "hi malan@x.edu !!" print Valid?

    Live — the SHAPE .+@.+ sits INSIDE the sentence, so re.search finds it anyway. This is 'contains', not 'is'. Predict, then Run.

    Valid — even though the whole string is plainly not an email. That's the mental model made concrete: re.search found the shape somewhere inside. Keep this leak in mind; anchors (two sections down) are the fix. First, more quantities.

    More quantities: * ? and counts {m,n}

    Three more pieces of machinery, all describing how many:

    • * — the thing before it, 0 or more times
    • ? — the thing before it, 0 or 1 time (optional)
    • {m} — exactly m times; {m,n} — between m and n times

    The -vs-+ difference is the one to feel: lets the part vanish, + insists it's there. Predict the result of the box, then try the swaps in the predict below it.

    Live — {2,3} is 'between 2 and 3', applied to the single 'a' before it. Try letters = "aaaa" (search still finds 3) and letters = "a" (too few). Predict first.

    Take the pattern r".@." (star, not plus) with email = "@". Valid or Invalid — and why?

    Valid. means 0 or more, so . happily matches nothing on each side — "@" alone fits .@. because zero characters before and after the @ is allowed. Swap to + (1 or more) and "@" becomes Invalid, because + insists on at least one character on each side. That one-character difference between and + is the whole point: lets the part vanish, + demands it be there.

    Now exercise ?. With re.search(r"colou?r", s), does it match both s = "color" and s = "colour"? What about s = "colouur"?

    Both "color" and "colour" match — u? means 'zero or one u', so the u is optional: drop it and you get color, keep it and you get colour. But "colouur" does not match the anchored r"^colou?r$", because ? allows at most one u, never two. That's ? in its pure form: the single token right before it appears 0 or 1 time — no more. (You'll reuse this exact move soon to make https? mean 'http or https'.)

    A quantifier applies only to the single token right before it. Given re.fullmatch(r"ab{2,3}", s) (whole-string match), which s does it accept?

    A quantifier binds to the one token immediately before it — here just the b. So b{2,3} means 'between 2 and 3 b's', and ab{2,3} is an a then 2–3 b's: "abb" or "abbb". With re.fullmatch, "aaabbb" fails because the whole string must fit (the leading aa has nowhere to go). (Heads-up: with re.search instead, "aaabbb" would match, since the stencil slides and finds the abbb at the end — that's the 'search hunts anywhere' idea. fullmatch is what makes this question single-answer.) To repeat a whole chunk like ab, wrap it: (ab){2,3}. And {2,3} is a count, never literal 2/3 characters.

    Escaping a literal dot, and raw strings

    Reach for the .edu ending and a trap springs. You might write r".+@.+.edu" — but that . before edu is the any-character wildcard, so it matches "...Xedu" too. To mean a literal dot, you escape it with a backslash: \.. Watch the broken version say Valid for a string with no real dot. Predict the result for "malan@harvardXedu" first.

    Live — the BROKEN pattern: an unescaped . is any-char, so "malan@harvardXedu" sneaks through. Predict Valid/Invalid, then Run.

    A dot is NOT a dot here

    Outside regex, . is just a period. Inside a pattern, . means any character except a newline — so r".+@.+.edu" happily matches "malan@harvardXedu", because that last . swallows the X. To mean a literal period you must escape it: \.. Same symbol, completely different job — read it by where it sits.

    "malan@harvardXedu" slipped through, because the wildcard . matched the X. Escape it as \. and only a real dot will do. But there's a second wrinkle: that backslash is the same escape character from Lecture 0 (\" for a literal quote inside a string), so in an ordinary string Python tries to interpret \. itself before regex ever sees it. The fix is the raw string r"...": the r tells Python to take backslashes at face value and pass them straight to the regex engine. That's why every pattern here starts with r. Predict: does the escaped, raw pattern reject "malan@harvardXedu"?

    Live — \. is a LITERAL dot; the r"..." raw string hands the backslash straight to regex. Now the X version is rejected. Predict first.

    Recall: the backslash escape, from Lecture 0

    A backslash is the Lecture 0 escape character — Python grabs it before the regex engine ever sees the pattern. A raw string r"..." switches that off, handing the backslash through untouched — so r"\." reaches re.search as a real \. meaning a literal dot. Habit: every regex pattern is r"...", even before it has any backslash. (One footgun: a raw string can't end in a single backslash.)

    Anchors ^ and $: match the WHOLE string

    Time to fix the leak you saw earlier (the shape found inside a sentence). re.search finds the shape anywhere, so r".+@.+\.edu" still matches "my email is malan@harvard.edu.". To demand the entire string be the email, pin both ends: ^ means start of string, $ means end of string. r"^.+@.+\.edu$" says 'from the very start to the very end, nothing but this shape.' Predict: with anchors, does "my email is malan@harvard.edu." pass?

    Live — ^ pins the start, $ pins the end, so extra words before/after now fail. Try email = "malan@harvard.edu" to see it pass. Predict first.

    Now it's Invalid — the leading my email is and the trailing . fall outside the anchored shape, so the whole string no longer fits the stencil. This is the single most common regex fix: anchor with ^...$ to turn 'contains the shape' into 'is exactly the shape' — exactly the leak (junk before the @) that sank the hand-written ladder. (One caution: with a bare .+@.+$ the greedy .+ would still swallow surrounding junk; it's the literal \.edu$ ending here that makes the anchor truly bite.)

    With re.search(r"cat", s) and s = "a category", what happens — and how do you make it require the whole string to be just cat?

    re.search looks for the pattern anywhere, so r"cat" is happily found inside "a category". To insist the whole string is exactly cat, anchor both ends: r"^cat$" — ^ at the start, $ at the end. That's the 'contains' vs 'is' distinction from the mental model.

    Character classes [...] and negation [^...]

    Even anchored, r"^.+@.+\.edu$" lets "malan@@@harvard.edu" through — .+ cheerfully matches those extra @s. You want 'one or more characters that are not an @'. Square brackets build a character class: [abc] matches any one of a, b, or c. Put a ^ inside the brackets and it negates — [^@] means any one character that is NOT an @. Heads up before you read the pattern: the next box uses ^ in both its jobs — the anchor at the very front, and the negation inside [...]. Read it left-to-right by position. Predict: does r"^[^@]+@[^@]+\.edu$" reject "malan@@@harvard.edu"?

    ^ means two different things — position vs negation

    Before you parse the next pattern: the same ^ symbol wears two hats. Outside brackets, at the start of a pattern, ^ is the anchor for 'start of string' (r"^cat"). Inside square brackets, as the first character, ^ negates the class ([^@] = 'not an @'). Same glyph, completely different jobs — read where it sits. ($ only ever means 'end of string'.) Also handy: most metacharacters lose their power inside a class — [a-z.] treats the . as a literal dot, no escape needed.

    Live — [^@]+ is one-or-more NON-@ chars, so triple-@ fails. The FIRST ^ anchors the string start; the one inside [] negates. Predict first.

    Ranges and predefined classes: \w \d \s

    Inside a class you can give a range with a dash: [a-z] is any lowercase letter, [a-zA-Z0-9_] is letters, digits, or underscore. Make that explicit pattern the username matcher first — it works, just verbosely. Predict: does "malan@harvard.edu" pass r"^[a-zA-Z0-9_]+@[a-zA-Z0-9_]+\.edu$"?

    Live — the explicit class [a-zA-Z0-9_] spells out letters, digits, underscore. It works, but it's a mouthful; the next cell shows the shorthand. Predict first.

    That [a-zA-Z0-9_] set is so common it has a one-letter shorthand: \w (a 'word' character) equals [a-zA-Z0-9_] exactly. Its friends: \d is a digit [0-9], \s is whitespace (space, tab, newline). Capitalize any of them to negate: \W non-word, \D non-digit, \S non-whitespace. So r"^\w+@\w+\.edu$" is the same shape as the cell above, just shorter. Predict: does "malan@harvard.edu" pass, and would "ma lan@harvard.edu" (a space) pass?

    Live — \w is shorthand for [a-zA-Z0-9_]. A space is NOT a \w, so try email = "ma lan@harvard.edu" and watch it fail. Predict first.

    Now that \d and the anchors ^...$ are both on the table, here's the payoff example I promised back in 'More quantities': the count braces {m,n} get a satisfying use. A phone number is 'exactly three digits, a dash, exactly four digits' — anchored to the whole string, that's r"^\d{3}-\d{4}$", built entirely from pieces you now know. Predict: does "555-1234" match, and would "55-1234" (only two leading digits)?

    Live — {3} is EXACTLY three, anchored start-to-end. Try phone = "55-1234" to watch {3} reject it. Predict first.

    Pocket cheat-sheet (so far) — quantities, one-char, anchors

    Quantities: 0+ · + 1+ · ? 0/1 · {m} exactly m · {m,n} m–n. One char: . any (not newline) · [abc] one of these · [a-z] range · [^@] not* this. Shorthands: \w = [a-zA-Z0-9_] (digits and _ too!) · \d digit · \s whitespace · capitals \W \D \S negate. Anchors: ^ start · $ end. We'll add a second card for |, groups and (?:...) once you meet them.

    With r"^\w+@\w+\.edu$", predict Valid/Invalid for email = "jane_doe@mit.edu" and for email = "jane.doe@mit.edu".

    "jane_doe@mit.edu" is Valid — the underscore _ is a \w character. But "jane.doe@mit.edu" is Invalid with this pattern, because . is not a \w character, so the dot in jane.doe breaks the \w+ run before the @. The takeaway here is exactly which characters \w covers — letters, digits, and underscore, and nothing else. (Real-world usernames do contain dots; a looser class like [^@]+ would accept them, at the cost of accepting more junk too.)

    Which class matches a single character that is not a digit?

    Capitalizing a predefined class negates it: \d is a digit, \D is a non-digit (likewise \w/\W, \s/\S). The wrong options: lowercase \d matches a digit (the opposite of what's asked); \w includes digits (it's [a-zA-Z0-9_]), so it's not 'non-digit'; and [0-9] matches the digit characters themselves, not their opposite. Also note \d is a single digit, so use \d+ for a whole number.

    Alternation | and groups (...)

    Real emails don't all end in .edu. The alternation bar | means 'this OR that': com|edu|gov matches any one of those. But | has the lowest precedence — left loose, r"^\w+@\w+\.com|edu$" actually means '(everything up to com) OR (just edu)', so the bare string "edu" would pass. Don't take that on faith — predict whether "edu" prints Valid, then Run the broken pattern and watch the leak.

    Live — the BROKEN ungrouped pattern. | binds loosest, so this means (...com) OR (edu$), and a bare "edu" sneaks through. Predict first.

    "edu" slipped through — the | split the entire pattern in two. To confine the choices, wrap them in a group with parentheses (...). Layering that group onto our same \w+@\w+ shape gives r"^\w+@\w+\.(com|edu|gov|net|org)$", which allows any of those endings — and notice that's exactly the previous \.edu$ cell with only the ending swapped for \.(...). Predict: does "malan@harvard.org" pass now, and would "malan@harvard.xyz"?

    A small deviation from the lecture

    CS50's lecture uses (com|edu|gov) — three endings. These notes use (com|edu|gov|net|org) (five) just for variety, so you see the | doing real work. Nothing conceptual changes; if you compare against the lecture's exact program, that's the one difference in this pattern.

    Live — (com|edu|gov|net|org) means any ONE of those endings; the parens keep | from leaking over the whole pattern. Try email = "malan@harvard.xyz". Predict first.

    Parentheses do two jobs at once

    (...) both groups (so | and + apply to the whole chunk) and captures (it remembers what matched, for .group() later — coming up). If you only need the grouping and not the captured text, write (?:...) — a non-capturing group. Heads up: that ? inside (?:...) is punctuation, part of the group's spelling — not the '0-or-1' quantifier you met earlier. We'll lean on (?:...) when we start counting groups.

    re.IGNORECASE: stop caring about case

    Patterns are case-sensitive by default, so the pattern rejects "MALAN@HARVARD.EDU" — the literal edu in the alternation only matches lowercase edu, not EDU. Rather than cram [a-zA-Z] everywhere, pass the flag re.IGNORECASE as a third argument: re.search(pattern, string, re.IGNORECASE) matches regardless of case. The pattern itself is unchanged from the last cell — the only new thing is the third argument. Predict: does the shouting address validate now?

    Live — same pattern as before; the ONLY change is the re.IGNORECASE flag as a 3rd argument. Try removing the flag to watch the uppercase address fail. Predict first.

    Optional pieces with ?: subdomains

    Some addresses have a subdomain: malan@cs50.harvard.edu. That's an extra word. chunk before harvard. Make a whole group optional by putting ? after it — ? is 'zero or one', the very quantifier you exercised on colou?r earlier, now applied to a whole group. (\w+\.)? means 'an optional word-then-dot chunk, appearing 0 or 1 time'. Slotting it in front of the domain gives r"^\w+@(\w+\.)?\w+\.(com|edu|gov|net|org)$" — again, exactly the IGNORECASE cell's pattern with one addition, the (\w+\.)? piece. It accepts both malan@harvard.edu and malan@cs50.harvard.edu. Predict: do both validate?

    Live — (\w+\.)? is an OPTIONAL subdomain chunk (0 or 1), the only addition to the previous pattern. Try BOTH email = "malan@harvard.edu" and email = "malan@cs50.harvard.edu". Predict each first.

    Both pass: with the subdomain present, the optional (\w+\.)? matches cs50.; without it, the ? lets the group match nothing. That ?-after-a-group move — 'this whole chunk is optional' — is one you'll reuse constantly. You now have the full matching toolkit, and the email pattern grew one honest step at a time: \w+@\w+\.edu → swap the ending for \.(com|edu|...) → add the re.IGNORECASE flag → add the optional (\w+\.)? subdomain. The rest of the lecture is about pulling text out of a match.

    Capturing groups and .group(): reformatting a name

    Beyond yes/no, regex can extract pieces. With plain string tools you'd write last, first = name.split(", ") — but that breaks the instant the spacing varies. Regex is sturdier: every (...) group captures the text it matched, and you read it back by number with .group(n) — .group(1) is the first parenthesized group, .group(2) the second, and .group(0) is the whole match. Note groups are 1-indexed here, unlike lists. Say a name arrives as "Last, First"; the pattern r"^(.+), (.+)$" captures the last name in group 1 and the first in group 2, and we rebuild it as group(2) + " " + group(1). Predict the greeting before you Run.

    Live — two capturing groups read by number: .group(1) before the comma, .group(2) after; .group(0) is the whole match. Predict the greeting.

    It flipped Malan, David into hello, David Malan. There's a second way to read the captures all at once: matches.groups() hands them back as a tuple you can unpack in one line. This box does the identical reformat with last, first = matches.groups(), and loosens the comma to , * (a comma then zero or more spaces) so messy spacing still parses. Predict the output.

    Live — .groups() returns a tuple (last, first) we unpack in one line. ", *" allows any number of spaces after the comma. Try name = "Malan,David". Predict first.

    Remember tuple unpacking, from Lecture 6

    In Lecture 6 you split a CSV line and dropped the pieces into two variables in one go — name, house = line.rstrip().split(","). matches.groups() hands back that same kind of tuple, so last, first = matches.groups() unpacks it the identical way — two capture groups, two names.     Guard the match: None has no .group()

    A match object is not the matched text — it's an object you ask for the text with .group(). And on no match, re.search returns None, which has no .group() at all. Call it blindly and you crash. This box (a these-notes demo, not from the lecture itself) searches for a digit in "abc" (there isn't one), so matches is None, then tries matches.group(). The traceback is the expected output here — you can't break anything. Predict the error before you Run.

    There it is: AttributeError: 'NoneType' object has no attribute 'group' — you called .group() on None. This is the regex twin of Lecture 3's hazard: there a bad line raised a ValueError and you learned to check before you touch; here a no-match hands back None and you must test it before reading it. The lesson is the same: always test the result before reading it. So far we wrote that as two steps — matches = re.search(...) then if matches:. Next we fold those into one line.

    The walrus := : assign and test in one line

    Notice the two-step shape in the name cells: call re.search, store it in matches, then test if matches. Python's walrus operator := does both at once: if matches := re.search(...): runs the search, assigns the result to matches, and tests its truthiness — all in the if. It folds the very test-before-you-touch-it guard from the None section just above (the same Lecture 3 lesson — a value you haven't confirmed must be checked before use) into one line, so matches is right there to use in the block. Predict the greeting (same as before).

    Live — the walrus := assigns AND tests in one line, guarding against the None crash you just saw. Same result as the two-line version, just tidier. Predict first.

    New here: the walrus :=

    A brand-new operator: := both assigns and tests in one line, so if matches := re.search(...): stores the match and checks it was found — exactly the guard-before-use you just built in the None section. It's pure convenience: the two-line matches = re.search(...) then if matches: does the identical thing. Read := as 'set, and also ask.' Don't confuse it with == (compare) or plain = (which can't go inside an if).

    re.sub: replace matches

    Matching and extracting aren't the only tricks — you can also substitute. Classic use: strip a URL prefix down to a username. With plain string tools you'd start simple — url.replace("https://twitter.com/", "") or the tidier url.removeprefix("https://twitter.com/") both chop a fixed prefix off. Predict what each prints.

    Live — the string-method lead-in: .replace and .removeprefix both strip a FIXED prefix. The next cell shows why regex wins when the prefix varies. Predict both first.

    Argument order: re.sub puts the string THIRD

    You drilled re.search(pattern, string) — pattern first, string second. re.sub is different: it's re.sub(pattern, repl, string) — pattern first, the replacement in the middle, and the target string moves to third. So the string you're operating on is in a different slot than in re.search. Mixing these up is a classic trip; when you switch verbs from search to sub, remember the string slid to the end.

    `?` again — same glyph, two roles

    You're about to see ? twice in one pattern, doing different jobs. In https? the ? is the '0-or-1' quantifier applied to the single preceding s — so it matches http or https (just like colou?r matched both spellings). In (www\.)? the ? is again the quantifier, making the whole (www\.) group optional. (Later, in (?:...), the ? will be neither — it'll be pure spelling for a non-capturing group.) Read each ? by what sits immediately before it.

    Both leave davidjmalan — but only because the prefix is exactly https://twitter.com/. The moment a URL might say http:// or include www., a fixed string can't keep up. That's where re.sub(pattern, repl, string) comes in: it replaces every part of string that matches pattern with repl. The pattern r"^(https?://)?(www\.)?twitter\.com/" matches an optional http:// or https:// (the s? makes just the single s optional), an optional www., then twitter.com/; replacing that with "" deletes it — whatever the prefix's exact form. Predict what's left of the URL.

    Live — re.sub(pattern, "", url): the string is the THIRD argument. s? makes just the s optional; (www\.)? makes www. optional. Try url = "http://www.twitter.com/davidjmalan". Predict first.

    The prefix is gone, leaving just davidjmalan — and now it'd survive http://, www., or both, which .replace could not. re.sub shines whenever you want to clean or rewrite text rather than just check it. Notice it's the same pattern machinery; only the verb changed from search to substitute (and the string slid to the third slot).

    Extracting with groups: from (.+) to non-capturing (?:...)

    Often you want the opposite of stripping: keep just the piece you care about. Match the whole URL but wrap only the username in a capturing group, then read it with .group(1). Start with the simplest username capture — (.+)$ for 'everything after the slash' — and an optional (www\.)?. Predict what .group(1) holds.

    Live — (.+)$ captures the whole username. But (www\.)? is ALSO a capturing group, so it took group 1 — watch which group the username lands in. Predict first.

We don't care about the www. text; we only need to group it so ? applies.     Pocket cheat-sheet (part 2) — combine and capture

    Now you've met all of these, here's the rest of the card: Combine: A|B this-or-that (lowest precedence — wrap it: (A|B)). Group + capture: (...) groups and remembers the text for .group(n). Group only: (?:...) groups without capturing — the ? here is spelling, not '0-or-1'. Read captures: .group(0) whole match · .group(1) first capture (1-indexed!) · .groups() tuple. Flag: re.IGNORECASE as the 3rd arg = case-blind (classes included). Verbs: re.search(pattern, string) · re.sub(pattern, repl, string) — string is 3rd!

    You write re.search(r"(https?)://(?:www\.)?(\w+)", url). How many capturing groups are there, and what is .group(2)?

    (?:...) groups without capturing, so it's skipped when numbering. The two capturing groups are (https?) = group 1 and (\w+) = group 2. .group(2) is therefore the site name, not www. (the wrong options assume (?:...) captures, or miscount). .group(1) is the protocol. That's exactly why you reach for (?:...) — to group without shifting your capture numbers, the bug you saw two cells ago.

    …and here's why you don't hand-write the REAL thing

    Honesty check, in the lecture's own spirit. Our pattern kills the junk the ladder waved through, but it isn't a real email validator — \w+ rejects hyphenated domains (a@my-server.com) and dotted usernames (jane.doe@...), and the single (\w+\.)? caps subdomains at one level. A spec-compliant email regex looks like this (do not type this from memory — the point is that you wouldn't):

    ^a-zA-Z0-9.!#$%&'+/=?^_{|}~-]+@[a-zA-Z0-9?(?:\.a-zA-Z0-9?)$`

    That monster is exactly why, in real code, you reach for a tested library instead of rolling your own. For Problem Set 7, match the spec you're given — not 'every legal email ever.'

    Going further — three names so they aren't a mystery later

    File these away; no need to learn them now. (1) re.fullmatch(pattern, s) does what ^...$ does — requires the whole string to match — without typing the anchors; this course sticks with ^...$ because seeing the anchors keeps the 'contains vs is' idea visible. (2) Quantifiers are greedy by default: re.search(r"^(.+), (.+)$", "Malan, David, Jr.") puts "Malan, David" in group 1 and just "Jr." in group 2, because .+ grabs as much as it can — adding a ? for lazy matching (.+?) flips the split to the first comma. (3) A greedy . on a tricky pattern over a huge* string can be slow ('catastrophic backtracking'); on the short inputs here it never bites. Three things that 'have a name' — meet them properly later.

    Your pattern r"^\w+@\w+\.edu$" keeps rejecting the real address "malan@harvard.edu" in your program, though it looks right. What's the most likely bug?

    A trailing space left on input() sits after the edu, so the anchored $ can't match the very end — the classic 'looks right but fails' bug, which is why CS50's originals call input("...").strip() before matching. (Subtle point: Python's $ does tolerate a single trailing \n, but a space or any other trailing char breaks it — so .strip() is the reliable habit.) The wrong options are all false: \w does match letters; dropping the anchors would only make it match more; and r"..." is the recommended way to write patterns.

    Common mistakes at a glance

    • re.search finds the pattern ANYWHERE in the string. r".+@.+\.edu" matches "my email is malan@harvard.edu." because the shape sits inside the sentence. Anchor with ^ (start) and $ (end) — r"^...$" — to require the whole string match. This is the 'contains' vs 'is' distinction, and the single most common fix (it's what kills junk hiding before the @).
    • . is the any-character wildcard, not a literal dot. r".+@.+.edu" wrongly matches "...Xedu". To mean a real dot, escape it: \.. (. does not match a newline by default; and inside a class [a-z.] the dot is already literal.)
    • Always write patterns as raw strings r"...". A backslash means something to both regex (\., \w) and Python's own escaping (the Lecture 0 escape character); the r hands backslashes to regex untouched, so the two don't fight. Make it a habit even before a pattern has any backslash. (A raw string can't end in a single backslash.)
    • is 0-or-more, + is 1-or-more, ? is 0-or-1. .@. matches a bare "@" (zero chars on each side); .+@.+ does not (it demands at least one). Picking where you meant + lets empty pieces sneak through. A quantifier applies to the single token right before it — one char, one class, or one (...) group.
    • ? wears more than one hat. Standalone, ? is the '0-or-1' quantifier (a?, colou?r = optional u, https? = optional s, (www\.)? = optional group). But in (?:...) that ? is spelling — punctuation that marks a non-capturing group, not a quantifier. Read each ? by what sits immediately before it.
    • ^ has two unrelated jobs. Outside brackets it anchors the start of the string (r"^cat"); as the first char inside a class it negates it ([^@] = 'not an @') — and a pattern like r"^[^@]+...$" uses both at once. Same symbol, read where it sits. $ only ever means 'end of string'.
    • Argument order differs between the verbs. re.search(pattern, string) puts the string second, but re.sub(pattern, repl, string) slides the string to third with the replacement in the middle. Don't carry the search habit over to sub.
    • Predefined classes: \w is [a-zA-Z0-9_] (letters, digits, and underscore — that's all, so a . or space breaks a \w+ run); \d is a single digit (use \d+ for a number); \s is whitespace. Capitalize to negate: \W \D \S.
    • | has the lowest precedence — confine it with parentheses. r"\.com|edu$" means '(everything up to com) OR (edu)', so a bare "edu" would pass; group the choices: r"\.(com|edu)$". Patterns are also case-sensitive by default — pass re.IGNORECASE (which folds case on character classes too, not just literals) instead of stuffing [a-zA-Z] everywhere or mangling the input with .lower().
    • A match object isn't the text, and no match returns None. Call .group()/.groups() to read the text; on no match re.search returns None, so matches.group() raises AttributeError: 'NoneType' object has no attribute 'group'. Always test first — the walrus if matches := re.search(...): assigns and tests in one line (it's assign-and-return, not ==).
    • Groups are 1-indexed, .group(0) is the whole match (not the whole string), and (...) both groups AND captures. .group(1) is the first (...); .groups() returns a tuple to unpack (Lecture 6's name, house = ...). Use (?:...) to group for ?/|/+ without capturing — every extra capturing group renumbers the ones after it (an optional (www\.)? quietly steals group 1).
    • Trailing whitespace breaks an anchored $. A stray space ("malan@harvard.edu ") fails r"...edu$" because of the hidden character at the end — exactly the 'looks right but fails' bug, which is why CS50's originals call input("...").strip() before matching. (Python's $ happens to tolerate one trailing \n, but not a space or anything else, so just .strip() and don't rely on it.)

    Recap & next step

    The one picture to carry away: a regex is a SHAPE the string is poured into, and re.search slides that shape along the text until it fits — so until you pin both ends with ^...$, you're only asking 'does this shape appear somewhere?', not 'is the whole string this shape?'. You felt that gap live: .+@.+ matched inside "hi malan@x.edu !!", the same looseness that waved "nonsense hi@there.edu" through the hand-written ladder. Anchoring with ^...$ is the fix — and one anchored pattern replaced the whole leaky ladder.

    The shorthand you built: re.search(pattern, string) returns a match object (truthy) or None (falsy); metacharacters . + ? {m,n} describe shape (always in a raw string r"...", with \. for a literal dot); ^ $ anchor; [...], [^@], [a-z], and \w \d \s say which characters; | alternates (wrap it in a group); re.IGNORECASE folds case. To extract*, (...) captures — read by .group(1) (1-indexed), .group(0) (whole match), or .groups() (a tuple to unpack); (?:...) groups without renumbering; guard None with the walrus if matches := re.search(...):; and re.sub(pattern, repl, string) rewrites text (mind the string in the third slot). The two cheat-sheet cards above hold the full table — lean on those.
