    Lecture 4 — Libraries

    You don't have to write everything yourself. You'll learn to import ready-made tools two ways, use random and statistics, read what a user typed on the command line, install other people's packages, fetch live data from an API, and write your own module.

    How these notes work (2 box types)

    White box, Run button = real Python, runs right here in your browser. Edit it, press Run. The first run downloads Python once (about 10 seconds), then it's instant.

    Greyed box, Copy only = no Run button, because it needs something a browser tab doesn't have (a terminal, installed software, or the internet). Copy it into a .py file and run it on your own machine; each greyed box shows the exact command.

    What you'll be able to do

    • Import a library two ways — import random (then random.choice) and from random import choice (then bare choice) — and know which call goes with which
    • Use random (choice, randint, shuffle) and statistics.mean, remembering shuffle mutates in place and returns None
    • Read command-line arguments via sys.argv[1:], guard them with len(sys.argv) and if/elif/else (or try/except IndexError), and bail cleanly with sys.exit(message)
    • Install packages with pip from PyPI, call an API with requests, and parse or pretty-print JSON with .json() (the IN door) and json.dumps(obj, indent=2) (the OUT door)
    • Tell what runs in your browser (the standard library) from what needs your terminal (pip, the network), and write a two-file module with from sayings import goodbye
    The one rule that explains everything below

    Each white box runs on its own, like its own tiny .py file. Names don't carry from one box to the next. That's why every box below re-types its own import random — it isn't redundant, it's required. If a box uses a tool, it must import that tool itself.

    (Keyboard, if you like it: Cmd/Ctrl + Enter runs a box; Esc steps back out of it. The mouse works fine too.)

    A problem you can't solve yet

    Say you want your program to flip a coin — pick "heads" or "tails" fairly, differently each time you run it. With only the tools from Lecture 0, you can't: nothing you've written makes a random choice. You'd have to invent randomness from scratch, which is genuinely hard to do well. This is the moment a library earns its keep.

    What a library is

    In Lecture 0 you wrote your own functions — square(n) took a number and handed one back. A library (also called a module) is just a file full of ready-made functions someone already wrote and tested. random knows how to pick things at random; statistics knows how to average numbers; json knows how to format data. You don't get them for free, though: you first import the file, which loads it and gives you a name to reach it by. We'll start with random.

    import: load the whole library

    import random loads the random library. Then random.choice([...]) reaches in and picks one item from a list at random — that's our fair coin flip, solved in two lines. (random.choice(...) is the same 'call a function' move as square(n); the name just lives inside a module now.) Re-run it and watch the result change:

    Live — press Run several times; random.choice picks heads or tails fresh each run.

    Never name your own file random.py

    A natural first instinct is to save your coin-flip program as random.py. Don't: if you then run python random.py with import random inside, Python tries to import your own file as the library and trips over itself — random.choice(...) crashes with AttributeError: partially initialized module 'random' has no attribute 'choice' (most likely due to a circular import). The 'circular import' hint means your file collided with the real one. Same trap for statistics.py, requests.py, and so on. Rule: never name your script the same as a library you import.

    from ... import: take just one tool

    If you only ever use choice, you can pull just that one function out with from random import choice and then call it bare — no random. in front. Same behavior, shorter call. Run it a few times:

    Live — same coin flip, called bare as choice(...) because we imported just that one name.

    Mental model — a library is a labeled toolbox

    You've now run both import styles. Here's the picture that ties them together: a library is a labeled toolbox, and there are two ways to get a tool out. The dot tells you which.

    import random — the whole box is in your room
    import random
coin = random.choice(['heads', 'tails'])
num  = random.randint(1, 10)
    import random puts the whole box in your room. Each time you want a tool, you open the box by name with a dot: random.choice(...), random.randint(...). The dot is you reaching in — and since the whole box is here, every tool is one dot away. (The toolbox picture is our own framing to make the dot click — CS50 doesn't teach it this way.)
    from random import choice — one tool on your desk
    from random import choice
coin = choice(['heads', 'tails'])
    from random import choice lifts just the one tool choice onto your desk, so you grab it bare, no dot: choice(...). But the box random itself never came to your room — only the single tool you named. So if you later reach for the box by name, it isn't there.
    Predict before you run it: you write from random import choice, randint (two tools, no box), then call them bare — choice([...]) and randint(1, 10). Both work bare, or do you still need a random. somewhere?

    Both work bare: from random import choice, randint puts both tools on your desk, so choice([...]) and randint(1, 10) each run with no dot. The dot is only for the box (import random). The trap is the reverse — if you imported only choice and then wrote random.randint(...), the box name random was never brought in, so it fails. Run the cell to confirm both bare calls work.

    Live — both tools imported by name, both called bare. Re-run for fresh values.

    And the reverse trap, just so you've seen the error once: this next box imports only choice, then reaches for random.randint — but the box name random was never brought in. This one is supposed to fail; you can't break anything. Run it to see the error, then read the line below:

    Live — supposed to crash. Run it to see the error, then read the next line. The fix is line 1: import random.

    That's a NameError: name 'random' is not defined — the same NameError you met in Lecture 3 (Exceptions). Here it just means the name random was never loaded. random.anything only works after a plain import random.

    More random tools: randint and shuffle

    random.randint(a, b) gives a random whole number from a to b — and unlike many Python ranges, both ends are included, so randint(1, 10) can return 1, 10, or anything between. Run it a few times:

    Live — re-run for a fresh number from 1 to 10 (both ends possible). A die would be randint(1, 6).

    random.shuffle(cards) reorders a list in place — it rearranges the very list you hand it, like shuffling a physical deck. Here we shuffle a tiny deck, then loop over it to print each card (the for-over-a-list from Lecture 2). Run it a few times to see the order change:

    Live — shuffle rearranges cards itself; then we loop to print. Re-run for different orders.

    Predict before you run it: a learner writes cards = random.shuffle(cards) and then print(cards). What prints — the shuffled deck, or something else?

    Something else: it prints None. Surprised? Run the cell below to see it, then read the callout for why — it's a trap almost everyone hits once. (And don't worry: this crash-free cell can't break anything; it's just a surprising result, not an error.)

    Live — the common mistake on purpose: assigning shuffle's result. Run it, then read why below.

    Why it printed None (Lecture 2's None)

    In Lecture 2 you met None, the no-value object. Here's where it bites. random.shuffle(cards) does its work to cards directly and hands back nothing — it returns None. So cards = random.shuffle(cards) throws your freshly shuffled deck away and stores None instead. shuffle isn't failing; it already shuffled the list. The rule: call random.shuffle(cards) on its own line, then just use cards. Never assign its result.

    A function tidy(deck) does random.shuffle(deck) inside and has no return line. You call result = tidy(my_deck). What is result, and what happened to my_deck?

    A function with no return line hands back None, so result is None. But random.shuffle worked in place on the list tidy was given, so my_deck itself is now shuffled. That's the whole point of in-place: the change lands on the original; the call returns nothing.

    statistics: averaging numbers

    New problem, new wall: you have a list of quiz scores and want the class average. You could sum them and divide by the count by hand every time — but the standard library already did that work. The statistics library gives you everyday math like averages: statistics.mean([...]) returns the average of a list of numbers.

    Live — the average of a list of scores. Edit the numbers and re-run.

    One small surprise about mean's type

    When the average comes out a whole number from int inputs, statistics.mean returns an int: mean([100, 90]) is 95, not 95.0. (CS50's video doesn't show the result; on modern Python it's the int 95.) When the average isn't whole, you get a float — mean([100, 91]) is 95.5. (That second example is ours, not from the lecture.) If you want a float every time, just divide yourself: sum(data) / len(data).

    You imported only choice with from random import choice, then wrote random.randint(1, 10). What happens?

    from random import choice brings in only the tool choice — never the box name random. So random.randint has no random to reach into, and Python raises NameError: name 'random' is not defined. To use random.randint, do a plain import random; to call it bare, from random import randint.

    Command-line arguments: reading what the user typed

    Here's a fresh wall. So far your programs run in a white box, or you'd input() to ask the user a question. But real command-line tools don't stop to ask — you tell them everything up front, like pip install cowsay (you'll type exactly that soon) or git clone .... You want python greet.py David to greet David immediately, no prompt. The words after the filename are command-line arguments, and reading them is the skill here.

    Why these boxes have no Run button

    A browser tab has no command line, so it has no arguments to read — sys.argv holds only an empty slot 0, and sys.argv[1] has nothing to reach. That's why every box in this section is greyed (terminal only): copy each into a .py file and run it in your own terminal, following the note on the box. Same reason every time, so I'll keep the later notes short.

    The sys library holds those typed words in a list called sys.argv ('argument vector'). The catch everyone hits: sys.argv[0] is the program's own filename, not the first word you typed. Your real arguments start at index 1, so for python name.py David, sys.argv[1] is "David".

    Terminal only — save as name.py, then: python name.py David

    import sys

# Run as:  python name.py David
print(sys.argv[0])   # name.py   <- the SCRIPT's own name
print(sys.argv[1])   # David     <- the first word YOU typed

print("hello, my name is", sys.argv[1])

    Now: what if the user runs python name.py with no name? Then sys.argv has only slot 0 (the filename), so sys.argv[1] reaches into a slot that isn't there and the program crashes with IndexError: list index out of range. This program shows the crash on purpose:

    Terminal only — save as name.py. python name.py (no name) crashes with IndexError; python name.py David works.

    import sys

# With no name typed, sys.argv is just ["name.py"] -> index 1 doesn't exist
print("hello, my name is", sys.argv[1])

    One way to handle that is the try/except you met in Lecture 3 — catch the IndexError the same way you caught a ValueError from int("cat"). If indexing fails, the user gave too few arguments:

    Terminal only — save as name.py. python name.py -> 'Too few arguments'; python name.py David -> greets David.

    import sys

try:
    print("hello, my name is", sys.argv[1])
except IndexError:
    print("Too few arguments")

    But except IndexError only catches too few — it can't notice too many names. The clearer guard is to check how long sys.argv is before you index, using the same len from Lecture 2. Here's the off-by-one to hold onto: because slot 0 is always the filename, one name given means a length of 2 (filename + name).

    Predict before you read on: the user runs python name.py David — exactly one name. What does len(sys.argv) equal?

    2. sys.argv is ['name.py', 'David'] — slot 0 is the filename, slot 1 is the name — so its length is 2, not 1. This is the lecture's signature off-by-one: 'exactly one name' is len(sys.argv) == 2, never == 1. The next cell prints the list and its length so you can see it on your own machine.

    Terminal only — save as args.py. Try: python args.py (len 1), python args.py David (len 2).

    import sys

print(sys.argv)        # e.g. ['args.py', 'David']
print(len(sys.argv))   # e.g. 2  ->  filename + one name

    Now guard the program with if/elif/else (Lecture 1): too few, too many, or exactly right. 'Exactly one name' is len(sys.argv) == 2:

    Terminal only — save as name.py. python name.py -> Too few; python name.py David -> greets; python name.py David Carter -> Too many.

    import sys

if len(sys.argv) < 2:
    print("Too few arguments")
elif len(sys.argv) > 2:
    print("Too many arguments")
else:
    print("hello, my name is", sys.argv[1])

    sys.exit: guard and bail out early

    There's a cleaner shape than wrapping the whole program in an else: check the inputs at the top, and if they're wrong, quit immediately. sys.exit(message) prints message and ends the program right there — nothing after it runs. This is the guard-and-bail pattern: bail out on bad input up front, then write the rest knowing the input is good. We keep both guards (too few and too many), each its own sys.exit. Notice the final print is un-indented — no else needed, because if the input was bad we never reached it:

    Terminal only — save as name.py. python name.py -> 'Too few'; python name.py David Carter -> 'Too many'; python name.py David greets David.

    import sys

if len(sys.argv) < 2:
    sys.exit("Too few arguments")
elif len(sys.argv) > 2:
    sys.exit("Too many arguments")

# We only reach here if exactly one name was given:
print("hello, my name is", sys.argv[1])

    Slicing a list

    To greet several names at once, you first need a way to grab 'everything except slot 0.' That tool is a slice. list[1:] makes a new list from index 1 onward. Two rules to lock in: the start index is included, and when you give an end index, that end is excluded. So nums[1:3] keeps index 1 and 2, but not index 3. Try it:

    Live — start included, end excluded. Edit the numbers to see the cut move.

    Now apply it to sys.argv. Since sys.argv[0] is always the filename, sys.argv[1:] is exactly 'the words the user typed' — loop over it with the same for-over-a-list to greet everyone:

    Terminal only — save as name.py, then: python name.py David Carter Emma

    import sys

# sys.argv[1:] = every word AFTER the script name
for name in sys.argv[1:]:
    print("hello, my name is", name)

    You run python greet.py Alice Bob. What is sys.argv[1:], and why slice it?

    sys.argv is ['greet.py', 'Alice', 'Bob']. The slice [1:] means 'from index 1 to the end,' so it drops the script name at index 0 and yields ['Alice', 'Bob'] — every word the user typed, and nothing else. Since slot 0 is always the filename, slicing it off is exactly how you loop over only the user's input.

    Packages and pip: installing other people's code

    random, statistics, and json come with Python. But what if you want a tool nobody at Python HQ wrote — say, a program that prints an ASCII-art cow saying your text? Millions of such libraries — packages — are published by other people on a site called PyPI (the Python Package Index). To use one you first install it with pip, a command you run in your terminal, not inside Python. Two distinct steps, easy to mix up: pip install (terminal, once) downloads the package; import (in your code) loads it so you can use it.

    Terminal only

    Run in your terminal: pip install cowsay, then save the code as say.py and run python say.py David.

    Terminal only — save as say.py. Swap cow for trex and re-run to get a dinosaur instead.

    import cowsay
import sys

if len(sys.argv) == 2:
    cowsay.cow("hello, " + sys.argv[1])
    # Try this too:  cowsay.trex("hello, " + sys.argv[1])
    Predict: you skip pip install cowsay and just write import cowsay at the top of your program, then run it. What happens?

    It crashes with ModuleNotFoundError: No module named 'cowsay'. import only loads a package that's already on your machine — it never downloads one. The fix is the two-step: run pip install cowsay in your terminal first (once), then import cowsay in your code. See the gotcha below for one extra wrinkle: the install name and the import name don't always match.

    pip install and import are TWO steps

    A big beginner trap: thinking import cowsay alone fetches the package, or that pip runs inside Python. It doesn't. The fix: run pip install cowsay in your terminal first, then import cowsay in your code. One real-world snag: the install name can differ from the import name — you pip install Pillow but import PIL. (Our examples, cowsay and requests, happen to match.)

    APIs: fetching live data from the internet

    Last wall, the most exciting one: you want live data — today's top songs, today's weather — that you could never type into a list yourself, because it changes by the minute. An API (Application Programming Interface) is a web address that hands back data instead of a web page, usually as JSON text. The requests package fetches it. requests.get(url) goes to the address and brings back a response object — and the response is not the data itself, a distinction we'll make hands-on in a moment.

    Terminal only — also needs the internet

    Run in your terminal: pip install requests, then save as itunes.py and run python itunes.py weezer. Use a single word like weezer so the URL just works. (Beyond this lecture: multi-word terms like 'taylor swift' need URL-encoding — ignore that for now.)

    Terminal only — save as itunes.py, then: python itunes.py weezer

    import requests
import sys

if len(sys.argv) != 2:
    sys.exit("Usage: python itunes.py SONG")

response = requests.get(
    "https://itunes.apple.com/search?entity=song&limit=1&term=" + sys.argv[1]
)

print(response.json())

    Notice response.json() in there: that's the call that turns the response into data you can use. That raw print is an unreadable wall of text, though. Before we tidy it, let's do the one piece of JSON you can try live, right here — no internet needed. The json library's json.dumps(obj, indent=2) takes a Python object and dumps it out as a tidy, indented string:

    Live — pretty-print a Python dict you typed yourself. Edit it and re-run to feel how indent works.

    Mental model — JSON has two doors

    Two functions move data across the JSON boundary, in opposite directions. Picture two doors — one IN, one OUT — and you'll never mix them up.

    The IN door — response.json() (text -> Python)
    response = requests.get(url)
data = response.json()        # text -> Python
songs = data['results']       # now you can index it
    response.json() is the IN door: it takes the JSON text the internet sent back and parses it into a Python dict/list you can index. After this call you're working with normal Python objects.
    The OUT door — json.dumps(obj, indent=2) (Python -> text)
    import json
print(json.dumps(data, indent=2))   # Python -> text
    json.dumps(obj, indent=2) is the OUT door: it takes a Python object and turns it into a pretty text string for a human to read. (Beyond CS50: json.loads(text) is the standalone IN door if your JSON is already in a string.)

    So back in the terminal, wrap the response in the OUT door and the wall of text becomes readable:

    Terminal only — same setup. python itunes.py weezer -> now the JSON is neatly indented.

    import json
import requests
import sys

if len(sys.argv) != 2:
    sys.exit("Usage: python itunes.py SONG")

response = requests.get(
    "https://itunes.apple.com/search?entity=song&limit=1&term=" + sys.argv[1]
)

print(json.dumps(response.json(), indent=2))

    Once you can see the shape, pull out just what you need. The parsed dict has a "results" key holding a list of songs; loop over it and print each one's "trackName". Bump limit to 50 for more results:

    Terminal only — same setup. python itunes.py weezer -> prints a list of matching track names.

    import requests
import sys

if len(sys.argv) != 2:
    sys.exit("Usage: python itunes.py SONG")

response = requests.get(
    "https://itunes.apple.com/search?entity=song&limit=50&term=" + sys.argv[1]
)

data = response.json()
for result in data["results"]:
    print(result["trackName"])
    This loop is pure Lecture 2

    Same dict-by-key and for-over-a-list from Lecture 2 — data["results"] reaches a list, result["trackName"] reads a value by key. The only new thing is where the data came from: the internet (through the IN door, response.json()) instead of a literal you typed. (data is just a name; CS50 calls it o.)

    Your own module: functions you can import

    Here's the secret that takes the magic out of modules: a module is not special — it's just an ordinary .py file full of functions, defined like square(n) in Lecture 0. random is someone's file of functions; so is statistics. When you write your own file of functions, you've made a module, and another file can import it. In a real project that's two separate files run from your terminal — so the two cells below are terminal-only, showing the real cross-file import. First the toolbox file, sayings.py:

    Terminal only — save as sayings.py. Just functions: this is your module. Running it directly does nothing visible; it's meant to be imported.

    def hello(name):
    print(f"hello, {name}")


def goodbye(name):
    print(f"goodbye, {name}")

    Now a second file, say.py, imports a tool from your own box. from sayings import goodbye takes the goodbye function out of your file — the same from ... import move as from random import choice, except the box is one you wrote. It even reads a name from the command line, just like the earlier name.py:

    Terminal only — save as say.py beside sayings.py, then: python say.py David

    import sys
from sayings import goodbye

if len(sys.argv) == 2:
    goodbye(sys.argv[1])

    To feel from ... import work without a terminal, here's a live version: we define goodbye and call it in the same box (one box can't span files), so you can press Run and see the call fire. On your machine it would be the two separate files above.

    Live — adaptation for the browser: goodbye defined and called in one box. On your machine, use the two-file version above.

    Common mistakes at a glance

    • The dot is the box. After import random, write random.choice(...) (reach in). After from random import choice, call it bare, choice(...) — and random.anything then raises NameError (Lecture 3's error), because from ... import brings in only the named tool, never the box itself.
    • random.shuffle returns None and changes the list in place. Never write cards = random.shuffle(cards) — that throws the shuffled deck away and leaves cards set to None. Call random.shuffle(cards) on its own line, then use cards.
    • statistics.mean's type follows the answer. For int inputs, a whole average comes back as an int (mean([100, 90]) is 95), otherwise a float (mean([100, 91]) is 95.5). Want a float always? Use sum(data) / len(data).
    • sys.argv[0] is the program's own filename, not the first word typed. Real arguments start at index 1, which is why 'one name given' means len(sys.argv) == 2, and why you slice sys.argv[1:] to loop over just the user's words.
    • A slice list[1:] returns a new list: the start index is included, an end index (if given) is excluded — nums[1:3] keeps index 1 and 2, not 3. A slice never returns a bare single item.
    • A browser cell has no command line, no pip, no internet. Every sys.argv, cowsay, and requests example is terminal only — run them in your own terminal, with the command shown on each box.
    • pip install and import are two different steps. pip install cowsay runs in your terminal (once) to download it; import cowsay runs in your code to load it. Importing without installing raises ModuleNotFoundError. The install name can differ from the import name (install Pillow, import PIL).
    • Reading sys.argv[1] with no argument raises IndexError. Guard by checking len(sys.argv) first (which also catches too many args), or catch it with try/except IndexError (the specific type, never a bare except). sys.exit(message) prints the message and stops the program right there.
    • Never name your own file the same as a library. Run python random.py with import random inside and Python imports your own file, crashing random.choice with AttributeError: partially initialized module 'random' ... (most likely due to a circular import). Same for requests.py, statistics.py.
    • requests.get(url) returns a response, not the data. Call response.json() to parse the JSON body into a Python dict/list you can index, like response.json()["results"].
    • JSON has two doors that run opposite ways. response.json() is the IN door — JSON text into a Python object you can index. json.dumps(obj, indent=2) is the OUT door — a Python object into a pretty text string.

    Recap & next step

    The big ideas, one line each:

    • The toolbox + the dot. import random puts the whole box in your room, so you reach each tool with a dot (random.choice, random.randint, random.shuffle). from random import choice puts one tool on your desk, so you call it bare (choice(...)) — and then random.anything raises a NameError.
    • random. shuffle rearranges a list in place and returns None, so never assign its result.
    • statistics. mean keeps the natural type — 95 (int) for a whole average, 95.5 (float) otherwise.
    • Browser vs terminal. Only the standard library runs in white boxes; sys.argv, pip, and requests are terminal only.
    • Command line. The filename sits in sys.argv[0], so real arguments start at index 1 (one name -> len is 2); guard with len(sys.argv) and if/elif/else (or try/except IndexError), bail with sys.exit(message), and slice sys.argv[1:] to loop over the user's words.
    • Packages. pip install (terminal) and import (code) are separate steps; pip pulls packages from PyPI.
    • APIs and JSON's two doors. requests.get(url) returns a response; .json() is the IN door (text -> Python dict), json.dumps(obj, indent=2) is the OUT door (Python -> pretty text).
    • Your own module. Just functions you can import — from sayings import goodbye mirrors from random import choice.
