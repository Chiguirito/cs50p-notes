    Lecture 6 — File I/O

    Everything your program builds in memory vanishes the instant it ends. This lecture makes data persist: you'll open a file to write and read it (closing it yourself first, then letting the with statement do it for you), store rows as CSV (first by hand, then with the csv module that survives commas inside a value), and finally peek at binary files by stitching images into an animated GIF with PIL.

    What you'll be able to do

    • Explain why a list built in memory is gone when the program exits, and open(name, mode) a file with "w" (overwrite — empties first), "a" (append to the end), or "r" (read, the default)
    • Write with file.write(...) — remembering it adds no newline, so you type \n yourself — and read back with file.read() (whole file), file.readlines() (a list), or for line in file:, stripping the trailing newline with line.rstrip()
    • Prefer with open(...) as file: over a bare open() plus file.close(), knowing with auto-closes even on error, and sort what you read with sorted(seq, key=lambda x: ...) or .sort(...) in place
    • Parse a CSV by hand with line.rstrip().split(",") and tuple unpacking, build a list of dicts, and feel exactly why that breaks the moment a value contains a comma
    • Reach for the csv module — csv.reader (rows as lists, row[0]), csv.DictReader (rows as dicts keyed by the header), csv.DictWriter (with fieldnames, writeheader, writerow) — and recognize that binary files like images need a library such as PIL

    Why files? Memory forgets

    Every variable, list, and dictionary you've built so far lives in your computer's memory, and memory is wiped clean the instant your program exits. Collect three names in a list, print them, and they're gone the moment the program finishes — nothing to come back to tomorrow. To make data persist, you write it to a file on disk. That's all File I/O is: Input from and Output to files, so your data outlives a single run.

    Why each file box writes before it reads

    Each runnable box starts fresh: a file written in one box is not visible to the next. So every box that reads a file first creates that file in the same box — it writes a few hard-coded lines, then reads them right back. (That box isolation is a property of these notes, not of normal Python; on your own machine a file you write stays put between runs.) You're free to edit the hard-coded data and Run again.

    "w" empties the file before your first write

Open names.txt with "w" to add one name and you've just deleted every name that was there. To add without erasing, you need a different mode — "a", right below.

    You're writing a program that should add one new line to a log file every time it runs, keeping all the old lines. Which mode do you open with — and what breaks if you pick the other one?

    A log that grows across runs needs "a" (append): it keeps what's there and adds to the end. "w" truncates the file to empty before writing, so each run would wipe every earlier line and leave only the newest — the classic way to lose data by reaching for the wrong mode. "r" can't write at all.

    with: let Python close the file for you

    Every box above used a bare open() and made you remember file.close(). The with statement removes that forgotten-close() bug entirely. with open(...) as file: opens the file, names it file (that's the as), runs the indented block, and closes the file automatically the moment the block ends — even if a line inside it raises an error. There's no close() to forget. Here's the append again, now in with form — and every box from here on uses with:

    Live and self-contained — the same append, now with with: no close() to forget. The indented block runs, then Python closes the file at its end.

    Mental model — open is a borrow, with is the auto-return

    A small picture for with. Opening a file is like borrowing a book from the library: it has to be returned. With a bare open() (what you used above), you must remember to give it back with close(). With with, the return is automatic the instant you're done — you literally cannot forget, even if something goes wrong mid-block.

    Bare open(): YOU must return it
    file = open("names.txt", "a")
file.write("Ron\n")
file.close()   # YOU return the book
    Miss the close() and the book is still checked out: writes may sit unflushed, the file stays locked. It works only if you never forget — and people forget. Worse, if a line above close() raises, you never reach it at all.
    with: returned automatically
    with open("names.txt", "a") as file:
    file.write("Ron\n")
# closed HERE, automatically
    The instant the indented block ends, Python closes the file for you — even if the block raised an error (the raise-and-stop from Lecture 3, the same error paths you wrote tests for in Lecture 5). Nothing to remember, nothing to leak.

    Why is with open("data.txt", "w") as file: preferred over file = open("data.txt", "w") followed by your own file.close()?

    with guarantees the file is closed when the block finishes — including if an exception is raised inside it. A bare open() puts that on you, and a forgotten close() can leave buffered writes unflushed or the file locked. Both can write and read; write never adds a newline either way; and with doesn't change disk speed.

    Reading lines: a list, or one at a time

    You've used file.read() (the whole file as one string) and the for line in file: loop (one line at a time, gentle on memory for huge files). There's a third option in between: file.readlines() reads the whole file at once and hands back a list of strings, one per line — handy when you want the whole list to index, count with len(), or sort directly. The catch is shared by both line-readers: each string keeps its trailing \n. This box shows exactly what readlines() returns. Predict before you run: is the \n still attached to each name?

    Live and self-contained — writes 3 names, then shows readlines() as a raw list. Watch the \n: it's still attached to every string.

    Lines keep their \n until you rstrip()

    readlines() gives ['Ron\n', 'Hermione\n', 'Harry\n'], not ['Ron', ...] — every line still carries its trailing \n. Looping for line in file: has the same issue. Forget to strip it and you get mysterious blank lines, or comparisons that silently fail because "Ron\n" != "Ron". The cure is line.rstrip(): with no argument it strips all trailing whitespace — the newline, spaces, tabs. (Both read() and readlines() also leave the file's cursor at the end afterward, so a second read in the same with block yields nothing — that's why our boxes re-open the file to read what they just wrote.)

    You loop the file but forget the strip: for line in file: print("hello,", line). What looks wrong in the output?

    A blank line after every greeting. Each line is still "Ron\n", and print adds its own \n on the end — so you get two \n total, which renders as one blank line between greetings. line.rstrip() removes the file's trailing \n so only print's newline remains. The same hidden \n is why "Ron\n" == "Ron" is False, which quietly breaks lookups and comparisons.

    CSV by hand: split on the comma

    Most real data has more than one field per row — a name and a house. The plainest way to store that is CSV (Comma-Separated Values): one record per line, fields separated by commas. You parse it by hand: read a line, rstrip() the newline, and split(",") it into pieces. A two-field line splits into a 2-item list, and name, house = ... drops each piece into its own variable in one go — that's tuple unpacking. We greet each student straight away.     One more: .sort() reorders in place

    sorted(seq, key=...) returns a new list and leaves the original alone. Its cousin .sort() takes the same key= but reorders the list in place — it changes the list itself and returns None. So students.sort(key=lambda s: s["name"]) followed by for student in students: prints the same order. Reach for sorted() when you want a new list, .sort() when you're happy to reorder the one you have.

    Hand over the lambda, don't call it

    sorted(seq, key=lambda s: s returns as if it were a function, raising TypeError: 'str' object is not callable. And remember: sorted(">"name"]) hands sorted a function to call for you, once per item — so you never add () after the lambda. Writing key=lambda s: s["name" returns a new list, while .sort() reorders the existing list in place and returns None.

    Why split(",") breaks: commas inside a value

    Hand-rolled split(",") works right up until a value itself contains a comma. Suppose the field isn't a one-word house but a home address like Number Four, Privet Drive. A real CSV protects such a value by wrapping it in quotes: Harry,"Number Four, Privet Drive". But split(",") knows nothing about quotes — it chops on every comma. (The official lecture motivates the csv module by swapping in this kind of data; here we isolate the crash so you can watch it.) Don't read ahead — let Run be the reveal.

    Live — a constructed demo that's SUPPOSED to fail on the unpack. Predict: how many pieces does split(",") give, and does name, home = ... survive? Then Run. The traceback is the expected output; you can't break anything.

    split(",") returned three pieces — it split on the comma inside the address — so name, home = ... raised ValueError: too many values to unpack (expected 2): you asked for 2 names but handed it 3 values. The comma inside the quoted field is exactly the case naive splitting can't handle — and exactly why the csv module exists.

    The csv module: reader and DictReader

    Python ships a csv module built exactly for this — import csv (the same import from Lecture 4). csv.reader(file) hands you each row already split correctly — it understands quoted fields, so the comma inside "Number Four, Privet Drive" stays put. Each row comes back as a list, indexed by number: row[0] is the name, row[1] the home.     Live and self-contained — csv.reader handles the comma INSIDE the quoted address. Each row is a list (row[0], row[1]); we build a list of dicts and sort, just like the by-hand version.

    Indexing by number is fragile: add a column or reorder them and every index silently points at the wrong field. csv.DictReader fixes that. It treats the first line as a header row and hands each later row back as a dict keyed by those headers — so row["name"] looks it up by key (reached by key, like the Lecture 2 dict), and your code keeps working even if columns get reordered.     Writing CSV: DictWriter

    Writing CSV has a matching tool: csv.DictWriter. You hand it the fieldnames (the column order), call writeheader() once to write the name,home line, then writerow({...}) for each record — a dict whose keys match the fieldnames. This single box writes the file and reads it straight back with DictReader. Two payoffs to predict: writeheader() writes the header so DictReader knows its columns, and DictWriter quotes any value containing a comma for you, so the addresses survive the round trip as single fields. Predict what the raw file shows around those commas, and what DictReader prints back.

    Live and self-contained — DictWriter with writeheader()+writerow (auto-quoting the comma in each address), then read back with DictReader in the SAME box. newline="" is the idiomatic way to open a file for csv writing.

    reader gives LISTS, DictReader gives DICTS

    Keep the two readers straight: csv.reader yields a list per row, so you index by number (row[0]); csv.DictReader yields a dict keyed by the header, so you index by name (row["name"]). Mix them up and you get a KeyError (row[0] on a dict) or the wrong field. For writing, DictWriter needs fieldnames=[...] and a dict-shaped writerow({...}); call writeheader() once before the rows if a later DictReader should find its header instead of mistaking your first record for the column names. Open the file with newline="" when writing CSV (as above) so the module's line endings aren't doubled into blank rows.

    Your CSV holds a value with a literal double-quote inside it, like He said "hi". A real CSV escapes that by doubling it: "He said ""hi""". Which read approach gives you the value back intact?

    The csv module implements the full CSV quoting spec: it handles values that contain commas, newlines, and escaped quotes (a doubled ""), restoring each field exactly. split(",") is blind to all of that — it only ever cuts on commas. That breadth, not just the comma case, is why the csv module exists; a CSV value absolutely can hold a quote, as long as it's escaped.

    Binary files: a look, not a lab

    The one idea here: binary files need a library

    A text file (names.txt, students.csv) is lines of characters — you open it, loop lines, split, rstrip. A binary file (a .gif, .png, .mp3) is raw bytes with no lines to read, so you don't parse it by hand: you hand it to a library that knows the format. The open/read/write idea is the same; only the tool changes with the kind of file.

    For images, that library is PIL (the Python Imaging Library, installed as Pillow with pip install pillow — a third-party package from PyPI, like cowsay and requests in Lecture 4). The classic CS50P example, costumes.py, takes image filenames on the command line and stitches them into a looping animated GIF: Image.open reads each frame, and one .save(...) call writes them out as a single GIF. The filenames arrive via sys.argv, the command-line list from Lecture 4 — and since sys.argv[0] is the program name itself, the code loops over sys.argv[1:] to get just the images, then stitches all of them with append_images=images[1:].

    Running these for real (and why this one is terminal only)

    Almost everything above runs right here in the sandbox; a few things only happen on your own machine. Append piles up across runs there (each run adds a line); the browser boxes simulate that with repeated "a" opens. And this costumes.py can't run in the browser at all: it needs a third-party pip install pillow, and it reads/writes binary image files passed as command-line arguments (sys.argv is empty inside a notebook cell). So this last one is a look, not a lab — read the shape, don't predict-and-Run.     Terminal only — save as costumes.py. Run: pip install pillow (once), then python costumes.py costume1.gif costume2.gif costume3.gif... Needs Pillow + real image files + command-line args, so it can't run in the browser.

    import sys

from PIL import Image

images = []

for arg in sys.argv[1:]:
    image = Image.open(arg)
    images.append(image)

# save_all=True writes every frame; append_images stitches ALL the rest; loop=0 loops forever
images[0].save(
    "costumes.gif",
    save_all=True,
    append_images=images[1:],
    duration=200,
    loop=0,
)

    Common mistakes at a glance

    • file.write() does not add a newline. It writes exactly the string you give it, so two write("Hermione") then write("Harry") calls produce HermioneHarry on one line. Type \n yourself when you want one record per line — print added one for you in Lecture 2; the \n escape itself is the backslash idea from Lecture 0.
    • open(name, "w") truncates the file to empty before writing — opening with "w" deletes whatever was there, before your first write. To add to a file instead of replacing it, use "a" (append). "r" (read) is the default when you pass no mode, so open("x") reads.
    • A file's cursor only moves forward. After one for line in file: (or read()/readlines()) it sits at the end, so a second read in the same with block yields nothing — re-open the file to read it again. (This is also why our self-contained boxes re-open to read what they just wrote.)
    • A forgotten file.close() is a real bug — buffered writes may never reach disk and the file can stay locked. You start with bare open()/close() to feel that; then prefer with open(...) as file:, which closes the file automatically when the block ends, even if an error is raised inside it.
    • Lines you read keep their trailing \n. Both file.readlines() and for line in file: hand you "Ron\n", not "Ron". Call line.rstrip() or comparisons fail ("Ron\n" != "Ron") and extra blank lines appear. read() returns the whole file as one string; readlines() returns a list (good for len/indexing/sorting); looping reads one line at a time (gentlest on memory).
    • Hand-rolled split(",") breaks on a comma inside a value. Harry,"Number Four, Privet Drive" splits into three pieces, and name, home = ... then raises ValueError: too many values to unpack (expected 2). This is exactly why the csv module exists.
    • csv.reader yields lists (index by number: row[0]); csv.DictReader yields dicts keyed by the header (index by name: row["name"]). Mixing them gives a KeyError or the wrong field. Prefer DictReader so reordering or adding columns doesn't silently break your indexing.
    • csv.DictWriter needs fieldnames, and writerow takes a dict whose keys match them. Call writeheader() once before the rows if you'll read the file back with DictReader — otherwise the reader treats your first record as the column names. Open the file with newline="" when writing CSV so the module's line endings aren't doubled into blank rows.
    • lambda s: s["name"] is just an unnamed function — the inline form of def get_name(s): return s["name"]. sorted(seq, key=lambda ...) calls it on each item for you; don't add () after the lambda (that calls the result and errors), and remember sorted() returns a new list while .sort() reorders in place and returns None.
    • Images and other binary files aren't text — you can't loop their 'lines'. Use a library that knows the format (PIL/Pillow for images, pip install pillow), and pass filenames via sys.argv from the terminal — sys.argv[0] is the program name, so the code slices sys.argv[1:] and stitches them all with append_images=images[1:].

    Recap & next step

    The one picture to carry away: memory forgets; a file remembers. Data in memory vanishes when a program ends — the gap the very first in-memory box opens — and files are how you close it, making data persist past a single run. You open(name, mode) a file — "w" overwrites (it empties the file first!), "a" appends to the end, "r" reads (the default) — and file.write(...) puts text in, adding no newline (you type \n yourself, the backslash escape from Lecture 0; print was the one that added a newline for you back in Lecture 2). You first closed files by hand with file.close(), felt how easy that is to forget, then switched to with open(...) as file:, which closes the file for you automatically, even on error (the raise-and-stop from Lecture 3, the same error paths you tested in Lecture 5) — so think of a file as a library book you borrow and must return, and with is the automatic return. To read, use file.read() (whole file as a string), file.readlines() (a list, handy for len/indexing/sorting), or loop for line in file: (one line at a time), and line.rstrip() away the trailing newline before you use or compare the text. Remember the cursor only moves forward, which is why each box re-opens to read what it just wrote.

    For multi-field rows you met CSV. By hand, line.rstrip().split(",") plus tuple-unpacking (name, house = ...) parses simple rows, which you collect into a list of dicts (the list-of-dicts shape from Lecture 2) and sort with sorted(students, key=lambda s: s["name"]) (new list) or students.sort(...) (in place) — the lambda being nothing more than an unnamed function (a Lecture 0 def with no name) that returns the sort key, learned on its own before applying it. But that hand-rolled split shatters the instant a value contains a comma ("Number Four, Privet Drive"), raising a ValueError on the unpack. That's the whole reason for the csv module: csv.reader returns each row as a list (row[0]), csv.DictReader returns it as a dict keyed by the header (resilient to reordering), and csv.DictWriter — with fieldnames, writeheader(), writerow({...}) per record, and newline="" on open — writes rows back out, quoting embedded commas for you.

    Finally, binary files (images, audio) are raw bytes, not lines, so you reach for a library: PIL/Pillow's Image.open and one .save(...) call stitch frames into a looping animated GIF, driven by filenames from sys.argv (the command-line list from Lecture 4, sliced [1:] past the program name) — a terminal-only program, a look rather than a lab, because it needs a pip install and real image files.

    Next up is Problem Set 6: you'll read a CSV, transform or clean its rows, and write a new file back out — pick csv.DictReader/DictWriter over hand-rolled split(","), and let with handle closing every file you touch.
