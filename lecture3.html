    Lecture 3 — Exceptions

    Programs shouldn't crash just because someone types the wrong thing. You'll see how Python signals a bad value, how to catch it instead of crashing, and how to keep asking until the input is good. By the end you'll have a small reusable helper you can drop into any program.

    What you'll be able to do

    • Tell a runtime ValueError apart from a SyntaxError caught before any line runs
    • Catch a ValueError with try/except instead of letting the program crash
    • Use else to run a line only when the try succeeded — and dodge the NameError trap
    • Loop with while True until a valid integer arrives, then leave via a reachable exit
    • Refactor into a reusable get_int(prompt) that returns the good value to its caller

    Remember: the L2 cliffhanger

    In Lecture 2, when we first read numbers in a while True loop, we warned that typing letters into int(input(...)) raises a ValueError that stops the program cold — and promised that handling bad text gracefully comes later. Later is now. This whole lecture is that one fix, built up step by step.

    Errors that happen while the program runs

    An exception is an error that happens while your program is running — a runtime error. The code is perfectly valid; it just hit something it couldn't handle on this particular run. Here's the int(input(...)) read-a-number move from Lecture 1's compare.py (input() itself goes back to Lecture 0): it reads text and turns it into a whole number, then an f-string prints it. Run it and type a real number like 7 — all good:

    Type a number like 7 — it prints fine.

    Before you run it: commit to an answer. If you run that same cell again but type the word cat instead of a number, does print still run, or not?

    It does not — the program crashes with a ValueError. Python can read the text cat fine, but int("cat") can't turn it into a whole number, so the program stops right there and print never runs. The exact message is ValueError: invalid literal for int() with base 10: 'cat' ("this string isn't a valid base-10 integer"). Now run it above and type cat to check.

    When int("cat") fails, we say Python raises a ValueError. "Raises" is the key verb: the failing line throws up its hands and stops the program mid-run. That's a runtime error — it only shows up when that line actually runs with bad input. Hold onto this verb; it's the one idea the rest of the lecture is built on.

    try and except: catch it instead of crashing

    We can't stop users from typing cat, but we can handle it instead of crashing. Wrap the risky line in a try block, and tell Python what to do if it goes wrong in an except block — naming the specific error you expect, ValueError. Now bad input prints a friendly message instead of a red traceback. Run it and type cat:

    Type cat — no crash, just "x is not an integer". Then re-run and type a number to see the normal path. (The print sits inside try for now; we fix that next.)

    Recall: SyntaxError, from Lecture 1

    You already met a SyntaxError in Lecture 1 — if x = 5: (one equals sign) wouldn't even run. That's the before-it-runs kind: Python can't even read the program, so it refuses to start and nothing runs at all. That's exactly why try/except can't catch it — there's no running program to catch the error mid-flight. A ValueError is the opposite: a valid line that raises mid-run, which is the kind you can catch.

    You type cat into int(input(...)) and the program stops with ValueError. How does this differ from a SyntaxError?

    A SyntaxError means Python can't even read your program, so it never starts — not one line runs. A ValueError is a runtime error: the program ran fine until a valid line (int("cat")) hit input it couldn't handle and raised. You can't catch a SyntaxError at runtime because the program never got to run; you can catch a ValueError, which is the rest of this lecture.
    Catch a SPECIFIC type — never a bare except

    Write except ValueError, naming the one error you actually expect. A bare except: (with no type) catches everything — including bugs you didn't mean to hide, like a typo'd variable name or a logic mistake, and even the Ctrl-C you'd press to quit. That turns a loud, fixable crash into a silent wrong answer. Catch the specific exception you're prepared to handle, and let real bugs surface.

    Mental model — the picture behind what just happened

    Now that you've seen the crash and the catch, here's the single picture that explains the rest of the lecture. When a line goes wrong, Python raises — like falling through a trapdoor in the middle of the try block. The instant a line raises, Python abandons the rest of the try right there and drops into except.

    The trapdoor in try
    try:
    x = int(input())   # if this RAISES...
    print(x)           # ...this line is SKIPPED
except ValueError:
    print('not an integer')
    A raise drops you out of try at that exact spot and into except. Everything after the failing line inside try is skipped. Hold this picture — the next section turns it into a surprise.

    The scope trap: a failed try leaves the name unassigned

    The print can't fail, so the tidy instinct is to pull it out of try — put it after the handler, where it looks cleaner. Try that. Type a number and it works. Now, before you re-run with cat, commit to an answer in the predict below.

    Move print out of try. Type a number first (works), then re-run with cat.

    Predict before running with cat: the except already printed "x is not an integer". So what does the final print(f"x is {x}") show?

    It crashes with NameError: name 'x' is not defined. The trapdoor: when int("cat") raised, Python jumped out of try before the assignment to x finished — so x was never created. The program then falls through to print(f"x is {x}") and tries to read an x that doesn't exist. That's a NameError: not a wrong value, but no name at all.

    Remember: None vs. a missing name (L2)

    In Lecture 2 you met None — a name that has a value, just the no-value one (it prints as None, no error). A failed try is different and worse: x was never assigned at all, so it doesn't exist. Touching a name that doesn't exist isn't None; it's a NameError.

    You typed cat, so x was never created. Where could you safely move print(f"x is {x}") so it never raises a NameError?

    The fix is to use x only on the path where the assignment definitely succeeded. Putting print after the handler runs it on both paths, including the failed one where x doesn't exist. Putting it in except runs it exactly when x is missing. What you want is a success-only path — and try has a block for exactly that, which is the next section.

    else: the success-only path

    You need x only on the path where it actually got created. try has a third, optional block for exactly that: else, which runs only when the try finished without raising — so x is guaranteed to exist there. (As a bonus, this keeps only the risky line in try, which is the tidy habit anyway.) Put the print in else: type cat and only the error message shows (no NameError); type a number and only the x is ... line shows.

    else runs ONLY on success. Type cat, then re-run and type 5. Watch which line appears each time.

    This else is NOT the if/else from Lecture 1

    You met else in Lecture 1 paired with if — "otherwise." On a try, else is the opposite trigger: it means "run this only if the try raised no exception." It runs on the success path and is skipped entirely when except fires — so exactly one of except (failure) / else (success) runs each time. Don't read it as "otherwise." (It's a genuinely uncommon clause — we use it here to make the success path obvious, and later we'll simplify it away once you trust it.)

    You have try (int) / except ValueError (message) / else. You add a SECOND print that also uses x. Which block must it go in to never raise NameError, and why?

    else runs only when the try raised nothing, so the assignment to x definitely completed — that's the one place x is guaranteed to exist. Putting it in try after int(...) works only if int didn't raise; putting it in except runs exactly when x is missing. Exactly one of except/else runs per attempt, and else is the safe home for the value.

    Loop until the input is good

    Catching the error is nice, but right now a bad answer prints a message and the program just ends. Better: keep asking until the user gives a real number. That's the same shape from Lecture 2 — a while True loop whose only way out is a reachable break (or, once we're inside a function, a return). Drop the whole try/except/else inside the loop, and put the break in the else (success) block: on a good number we leave the loop; on cat we print the message and loop round to ask again.

    Type cat a couple of times, then a number — watch the output and count the messages.

    Predict: if you type cat, then dog, then 8, how many times does "x is not an integer" print, and what's the final line?

    "x is not an integer" prints twice (once for cat, once for dog), then 8 succeeds: the else runs break, the loop ends, and the final line is x is 8. Each bad answer triggers except and loops round; the first good answer reaches break in else and leaves. The loop only ends on a valid integer. (Note: x is still readable after the loop — Python loops don't create their own scope.)

    while True needs a reachable exit

    Lecture 2's rule: while True has no condition that turns False, so the only way out is a break (or return) your code can actually reach — here, the instant you type a valid integer. That reachable escape is what guarantees the loop ends. (And on this page a live while True cell can't freeze, because each pass blocks on the input() pop-up while it waits for you — more on that in the page tips at the bottom.)

    Refactor into a function that returns a value

    Where we are

    You now have a working loop. From here we'll change one thing per step until get_int is a small, reusable helper — you only need to track a single delta from one cell to the next.

    "Ask until you get a valid integer" is a self-contained job you'll want again and again — so give it a name and make it a function. get_int() holds the loop and returns the good value; main() calls it and prints the result. Defined first, called last — the define-main-first habit from Lecture 1.

    get_int() loops, then returns x after the break. main() uses it. Type cat then a number.

    Mental model — return does double duty

    Look at the flow inside get_int(): loop until else runs break, fall out of the loop, then return x. The break and the return x are two steps doing one job — and now that we're inside a function, one keyword can do both.

    return ends the loop AND the function
    def get_int():
    while True:
        try:
            x = int(input())
        except ValueError:
            ...
        else:
            return x   # leaves the loop AND the function — and hands x back
    A return inside the loop ends the function — which also leaves the loop — and hands the value back, all at once. That one move replaces a break plus a separate trailing return. So we can return x straight from the else:

    else now returns x directly — no break, no trailing return. Type cat then a number.

    Streamline: return straight from inside try

    Now that the success path is just return x in else, look at what the try can do: it either converts and returns, or it raises — there's no third outcome. So we don't need the else at all. Move the return up into the try: convert the input and return it in one line. If conversion fails, control jumps to except and the while True simply loops round again. No else, no break, no temporary variable:

    return int(input(...)) does it all: convert, and if it works, leave the loop AND the function together. A ValueError is caught and the loop re-asks. Type cat then a number.

    In get_int(), why can return int(input(...)) replace the whole else: return x step?

    Inside the try, the line has exactly two outcomes: a successful int(...) returns immediately (leaving loop and function together), or a failed one raises and except handles it, looping round. There's no success-but-don't-return case, so the else is redundant. The loop still always terminates — but only the moment a valid integer reaches the return.

    pass: a silent re-prompt

    That last version prints a message on every fumble — which is friendly for a confused first-timer. But in a tight retry loop, a quick double-typo can scroll noise. Neither is always right: a message helps, silent re-prompting feels calmer — it's the caller's call. To show the silent option, we need Python's keyword for "do nothing", because except needs something in its body and can't be left empty. That keyword is pass: a valid, empty placeholder. Put it in the except and a bad answer is swallowed silently; the loop just re-asks with no message.

    pass = do nothing. Type cat, then a number to finish. Watch the output between tries.

    Predict: with except ValueError: pass, you type cat. What gets printed before the prompt comes back?

    Nothing. pass means "do nothing," so the except block runs but prints no message and forwards nothing — it just lets the loop go round and show the input prompt again. (Don't confuse pass with Lecture 2's continue: continue jumps back to the top of the loop, while pass does nothing and simply falls through.) The only visible thing is the prompt reappearing. Note we still catch the specific ValueError — a bare except: pass would silently swallow real bugs too, which is a genuine anti-pattern.

    Parameterize the prompt: a truly reusable get_int

    One last touch. Right now get_int() always asks "What's x?" — useless if you want a different question. Give it a parameter, prompt — just as square(n) in Lecture 0 took its number as a parameter (called as square(x)) — and pass it straight to input(prompt). Now the caller decides the wording, so the same function works anywhere: get_int("What's x? "), get_int("How old are you? "), anything.

    Final form: get_int(prompt) is reusable — the caller supplies the question. Type cat then a number.

    Predict: call BOTH get_int("What's x? ") and get_int("How old are you? ") from the same main. How many times is the function defined, and what makes the two calls behave differently?

    The function is defined once. The two calls differ only because each passes a different prompt string, which get_int hands straight to input(prompt) — nothing inside the function changes. That's the whole point of a parameter: one definition, behavior the caller controls. From a one-line int(input(...)) that crashed on cat, you've built a robust, reusable "get me a valid integer with this prompt" you could drop into any program — picking up try, except, else, pass, and a sharper sense of return along the way. (Want active recall? Write get_positive_int(prompt) that loops until the answer is a non-negative integer.)

    Beyond this lecture — coming from C, Java, or JavaScript? (skip unless you know one)

    It's try/except, not try/catch — and Python says a line raises a ValueError, not "throws" an exception object. More surprising: in Python, using exceptions for ordinary input validation (try to convert, handle the failure) is normal, idiomatic control flow, not a last resort — the opposite of the advice you may have heard in other languages.

    Page tip — the input() pop-up and Cancel

    input() shows a pop-up and echoes what you type into the output. A live while True cell on this page never freezes because each pass blocks on that pop-up, waiting for you — so it can't spin even though the condition is always True. The reachable break/return is still what ends the loop once you enter a number.

    Pressing Cancel stops the cell — but note: in standard Python a cancelled input() raises an EOFError, a different error from the ValueError we catch, so these except ValueError loops would not handle it; Cancel works here only because the runtime ends the run for you. If anything ever seems stuck, reload the tab (that also resets the shared Python session).

    Common mistakes at a glance

    • A ValueError is raised at runtime — the line was valid until it met bad input (int("cat")). A SyntaxError (Lecture 1's if x = 5:) is different: Python can't even read the program, so it's caught before any line runs. You can try/except the runtime kind, never the syntax kind.
    • Catch a specific type: except ValueError, never a bare except:. A bare except swallows everything — real bugs (a typo'd name, a logic error) and even Ctrl-C — turning a loud crash into a silent wrong answer.
    • Put only the risky line inside try (the int(input(...))). Wrapping extra lines lets try quietly hide problems that have nothing to do with the error you meant to handle.
    • A failed try leaves the name unassigned: the raise jumps out before x = ... finishes, so x was never created, and using it later is a NameError. Unlike Lecture 2's None (a name holding the no-value object), here x doesn't exist at all.
    • else on a try runs only on success (no exception raised) — the opposite trigger from the if/else of Lecture 1. Exactly one of except (failure) or else (success) runs per attempt; else is the safe place to use the value.
    • while True has no condition that turns False, so it needs a reachable break (or return) — here, the moment you type a valid integer. That reachable escape, not the runtime, is what makes the loop end.
    • A return inside the loop exits both the loop and the function at once — which is why it replaces both break and the trailing return x. And since the try line either returns or raises, no else is needed at all.
    • pass means do nothing — a valid empty placeholder so a block that needs a body (like except) can have one. Unlike Lecture 2's continue (which jumps to the top of the loop), pass doesn't print, skip, or forward the error; it just lets control fall through. Pairing pass with a bare except is the anti-pattern.
    • Give get_int(prompt) a parameter so the caller picks the question. A hard-coded prompt makes the function un-reusable; input(prompt) makes the same validator work for any "ask for a number" need.
    • Page-specific: Cancel on a pop-up only stops the cell because the runtime ends the run — in standard Python a cancelled input() raises EOFError, which except ValueError would not catch.

    Recap & next step

    You can now keep a program alive when a line blows up at runtime. The trigger is int(input(...)), which raises a ValueError on text like cat — a runtime error, unlike the SyntaxError you met in Lecture 1, which Python catches before a single line runs. This pays off the promise from Lecture 2. The fix is try (wrap only the risky line) plus except ValueError (catch the specific type, never a bare except). The hardest idea is the trapdoor: a raise abandons the try mid-statement, so a name the failing line was about to assign is never created — which is why pulling print outside try gives a NameError. Here x doesn't exist at all, unlike Lecture 2's None, which is a value. else fixes it by running only on success, where the value is guaranteed to exist. From there it's a while True helper retold: a loop with a reachable escape keeps asking until the input is good, and folding it into a value-returning get_int() lets return do double duty — leaving the loop and the function — so first else: return x drops the break, then return int(input(...)) drops the else too. pass makes the handler silent (a do-nothing choice, not always the right one), and a prompt parameter makes get_int(\"What's x? \") reusable anywhere. Next up is the problem set: reach for try/except ValueError whenever you convert user input, keep only the risky line in try, remember else is the success path, lean on return to leave a loop, and skim the Common mistakes above — most exception bugs are right there.
