    Lecture 5 — Unit Tests

    Eyeballing your output doesn't scale. You'll learn to write code that tests code: keep your tests in a file beside your program, state a fact with the built-in assert, watch a wrong answer raise an AssertionError, report more than one failure (first by hand with try/except, then for free with pytest), check that bad input fails the right way, and discover why a function must return — not print — to be testable.

    How these notes work

    White box, Run button = real Python, runs right here. Edit it, press Run (or Cmd/Ctrl + Enter); press Esc to step back out. The first run downloads Python once (about 10 seconds), then it's instant.

    Each runnable box starts fresh — variables and functions from one box don't carry into the next, so each box re-defines what it needs. That matters below: a few boxes deliberately re-paste a broken square so you can watch a test catch it. When that happens, the note on the box says so.

    What you'll be able to do

    • Keep tests in a separate test_*.py file that borrows the function under test with from calculator import square
    • Write assert CONDITION checks, reading silence as a pass and a False assert as an AssertionError that halts — the raise-and-stop you met in Lecture 3
    • Group checks into test_ functions, knowing one passing case can hide a bug a second case catches — n + n equals n * n only at 0 and 2
    • Use pytest (a terminal tool) to run each test_ function independently and report every failure for free, and pytest.raises to test error paths
    • Make a function testable by returning its result rather than printing it (Lecture 0's square/None lesson), and organize tests into a test/ package with an empty __init__.py
    Do this before every Run: predict

    Before you press Run, say what you expect. For testing, the choice is almost always between just two outcomes: nothing visible (silence), or an error that stops the program. Testing trips people up because the right answer is often nothing visible — and "nothing happened" feels like "nothing ran." Predicting first turns each surprise into a lesson.

    Why test your own code?

    Until now you checked your programs by eyeballing the output — run it, type something, see if it looks right — or you leaned on CS50's automatic checks. That works for a tiny program, but it doesn't scale: real programs have dozens of functions, you change one line, and you quietly break another. Professionals fix this by writing code that tests their code: small checks that run in a second and shout the moment something is wrong. That's a unit test — a check on one small piece (one unit) of your program.

    All lecture we'll test one tiny function, square(n) — the very function from Lecture 0, where you saw that print(n n) hands back None but return n n hands back the value. It returns n n, so square(2) should be 4 and square(3) should be 9. It's simple enough that the right answer is obvious, which lets us focus on the testing*, not the math — and that Lecture 0 print-vs-return contrast comes back to bite us at the very end.

    Two files: the program, and the test beside it

    From the start, real projects keep your code in one file and your tests in a separate file that borrows the function under test. So here is the program, calculator.py. It asks for a number and squares it; square does the actual work.

    Terminal only — save as calculator.py. The if __name__ line just decides whether main() runs when you run this file directly; ignore it for now (Lecture 4 mentioned it in passing too).

    def main():
    x = int(input("What's x? "))
    print("x squared is", square(x))


def square(n):
    return n * n


if __name__ == "__main__":
    main()

    The test lives next door in test_calculator.py. Its first line, from calculator import square, means go find calculator.py next door and borrow its square function — the same from ... import move you used in Lecture 4 (from sayings import goodbye, from random import choice), except now the file you borrow from is your own.

    The clumsy first version: if / print

    Here's the most obvious way to test square with no new tool: check the answer with an if and print a complaint when it's wrong. It works — but watch how verbose it gets, because every check needs its own if and its own message.     Nothing printed, because both checks were fine — but look at the cost: two lines of if/print per fact, and a typo'd message is its own silent bug. Python has a built-in keyword that says the same thing in one word: assert.

    assert: state a fact you believe is true

    The keyword assert takes a condition and says "this had better be true." Write assert square(2) == 4: if square(2) really is 4, the condition is True and assert does absolutely nothing — no output, the program just rolls on. That silence is the test passing. We keep the checks inside a test_square() function (the shape pytest will want later) and call it at the bottom so it runs here. The trailing print is ours: since a passing test is silent, that line is our only proof execution reached the end.

    Live — predict first: what does this print? Then Run.

    assert is a statement, not a function — no parentheses

    You just typed assert for the first time, so bank the one rule that matters: write assert square(2) == 4 with no wrapping parentheses. If you want a message, the comma goes outside: assert square(3) == 9, "square(3) should be 9". (The trap of writing assert(cond, "msg") instead is in the gotchas appendix — skip it for now.)

    Mental model — a test is a tripwire

    Here's the picture to carry through the whole lecture, and it's the engine behind every testing tool: an assert is a tripwire strung across a fact you believe is true. You've just run a passing one — silent. Next you'll trip one on purpose.

    A passing test is silence
    assert square(2) == 4   # step over: silence
assert square(3) == 9   # step over: silence
    Step over the wire cleanly — the fact is True — and you hear nothing. That silence is the test passing, not the test failing to run. Beginners read silence as 'it didn't run'; flip it — silence means it ran and passed.
    A tripped wire is a WIN
    def square(n):
    return n + n   # broken
assert square(3) == 9   # foot catches the wire
    A False condition catches the wire: the alarm fires (an AssertionError is raised) and you stop dead, right there. Lines after it never run. Tripping the wire isn't failure on your part — it's the wire succeeding. A red failure is the test earning its keep by catching a bug before your users do.

    A failing assert: watch the tripwire trip

    Let's trip the wire on purpose. Each box starts fresh, so we re-paste square here — this time deliberately broken: it does n + n instead of n n. Two asserts run in a row. Predict before you run: which one trips the alarm — the first or the second*? This box is supposed to fail — run it to see the AssertionError; you can't break anything.

    With the broken square (which does n + n), which assert trips first — square(2) == 4 or square(3) == 9?

    The second one trips. Quirk to remember: n + n equals n * n only when n is 2 (and 0). So square(2) gives 2 + 2 == 4 — the first assert passes silently. But square(3) gives 3 + 3 == 6, not 9, so the second assert raises an AssertionError and halts; the final print never runs. Run it and watch.

    Live — supposed to FAIL. Run it to see the AssertionError. The broken square does n + n on purpose.

    Why one passing test isn't enough

    As you predicted, the alarm fired on the second assert. That is the whole reason you test more than one value: the broken n + n still passes square(2) == 4, because 2 is one of the only two numbers (2 and 0) where n + n equals n n. If you'd tested only square(2), you'd have shipped a broken function with a green light. The bug surfaces on square(3) (3 + 3 is 6, not 9) — and later, that's why we test positive, negative, and* zero, not just one lucky case.

    A teammate runs your test cell — assert square(2) == 4, then print("done") — and says "nothing printed except 'done', so the test must not have run." What do you tell them?

    A passing assert produces no output — that silence is exactly what passing looks like. The done line printing afterward is the giveaway: execution rolled right past the assert without tripping it. If the assert had failed, it would have raised an AssertionError and halted, so done would never have printed.

    Reporting more than one failure: try / except

    A plain chain of asserts halts at the first failure, so it can only ever tell you about one bug at a time. You can work around that by hand: wrap each assert in a try/except AssertionError that catches the trip and prints a message instead of halting. Now every check runs, and every failure gets reported. Below, square is broken (n + n) again. Predict: with two checks, how many lines print?

    Live — broken square (n + n) re-pasted on purpose. Predict first: how many lines print? Then Run.

    One line printed: square(3) failed and got reported, while square(2) slipped through (because 2 + 2 happens to equal 4). The win is that the program didn't halt at the first problem — it ran both checks and reported what broke. But look at the cost: each check is now a three-line try/except/print block, and every message is hand-typed and could itself be wrong. That verbosity is the problem pytest will solve.

    Where assert belongs

    One boundary to keep straight: assert checks your code; try/except (Lecture 3) handles the user's input. Use assert to catch your own bugs while you're developing. Use try/except to handle whatever a user types. Don't reach for assert to validate user input.

    Heads-up: the Run button goes away here

    assert and try/except are built into Python, so every white box above ran for real. pytest is not — it's a third-party tool you install with pip from PyPI, exactly like cowsay and requests in Lecture 4, and you run it from your terminal, not from inside Python. So most boxes from here down are greyed (terminal only): copy the files onto your own machine, run pip install pytest once, then pytest test_calculator.py. From here you predict, then verify on your own machine — and one box below is live again, clearly tagged.

    pytest: run every test, report every failure for free

    Calling test_square() yourself works for one function, but real projects have dozens of tests across many files. pytest is the standard tool that finds and runs them all. Here is test_calculator.py rewritten the way pytest wants it: split into separate test_ functions instead of one. pytest finds tests by two naming rules — the file must be named test_.py, and each test function must start with test_. This also lets us introduce the cases the failing-assert gotcha promised: a good test tries a positive, a negative, and* zero, so each lands in its own function.

    Terminal only — save as test_calculator.py beside calculator.py. Then: pip install pytest (once), then pytest test_calculator.py

    from calculator import square


def test_positive():
    assert square(2) == 4
    assert square(3) == 9


def test_negative():
    assert square(-2) == 4
    assert square(-3) == 9


def test_zero():
    assert square(0) == 0

    Splitting into separate test_ functions is how pytest gives you the report-everything behavior you built by hand — with zero boilerplate. It runs each test_ function independently, so a failure in test_positive doesn't stop test_negative or test_zero. One pytest run shows every failing test at once: a red F for each that failed, a green dot for each that passed.

    You rename test_zero to check_zero and run pytest test_calculator.py. Does pytest run the zero check?

    No. pytest only runs functions named test_*. Renamed to check_zero, it's silently skipped — no error, no warning. When a test seems to be ignored, check the prefix first.

    You can't run pytest in a browser, but you can feel the payoff. This live box is a hand-rolled stand-in that mimics pytest's per-test output: a tiny report helper prints PASS or FAIL for each check on its own line, so more than one failure shows up in a single run. The square here is broken (n + n). Predict: how many FAILs print? Then Run.

    Live — a stand-in that MIMICS pytest's per-test PASS/FAIL output. Broken square (n + n) on purpose. Predict the FAIL count, then Run.

    Two FAILs print: positive (3 + 3 is 6, not 9) and negative (-2 + -2 is -4, not 4). zero prints PASS, because 0 + 0 equals 0 0 — zero is the other number where the broken n + n accidentally agrees with n n. Important: you won't write report() yourself. This cell only mimics pytest's output so you can see it in the browser. With real pytest you write plain asserts inside test_ functions, and pytest prints the F-and-dot summary for you — no report, no try/except, no boilerplate.

    test_calculator.py has test_positive, test_negative, and test_zero. Both test_positive and test_zero are broken. What does one pytest run report?

    pytest runs each test_ function independently, so one failing test never silences another — you get a red F for test_positive and a red F for test_zero in one run, plus a green dot for test_negative. A plain chain of asserts, by contrast, halts at the first AssertionError.

    Testing the error path: what should NOT work

    Good tests don't only check that correct input gives the right answer — they also check that wrong input fails the right way. What does square("cat") do? It tries to compute "cat" "cat", and Python won't multiply a string by another string — "cat" 3 works fine (it's "catcatcat", the repetition you've seen), but string-times-string doesn't. The result is a TypeError. A good test asserts that this error genuinely happens. Heads-up: this next box is LIVE again (try/except is built-in) before we return to terminal-only pytest boxes.

    What does square("cat") do — return a weird string, or raise something? If it raises, which exception?

    It raises a TypeError. square("cat") computes "cat" "cat", and Python won't multiply one string by another (the message is can't multiply sequence by non-int of type 'str'). String times int repeats; string times string* raises. So it doesn't quietly misbehave — it raises, which is exactly the error path a good test pins down.

    Live — catching the error with try/except. square('cat') is 'cat' * 'cat', which raises TypeError.

    That try/except TypeError is structurally identical to Lecture 3's try/except ValueError — you're proving the error happened. pytest expresses the same idea with pytest.raises: "this block must raise a TypeError." Here's the complete test_calculator.py with the error-path test folded in — note import pytest at the top:

    Terminal only — the FULL test_calculator.py. Run: pip install pytest (once), then pytest test_calculator.py

    import pytest

from calculator import square


def test_positive():
    assert square(2) == 4
    assert square(3) == 9


def test_negative():
    assert square(-2) == 4
    assert square(-3) == 9


def test_zero():
    assert square(0) == 0


def test_str():
    with pytest.raises(TypeError):
        square("cat")
    Terminal only — put just the failing call in the with block

    Inside with pytest.raises(TypeError):, put only the call you expect to fail. Once it raises, pytest is satisfied; any follow-up assertions belong after the with block, not inside it.

    The key lesson: a function must RETURN to be testable

    Here's the most important idea in the lecture, and it decides whether any of the above even works. Suppose you have a greeting function in hello.py that just prints its greeting, and you write a test for it: assert hello("David") == "hello, David". The text hello, David clearly shows on screen when you call it — so predict before you run: does the assert pass, fail with an error, or something stranger? Most people guess it passes. This cell is supposed to fail; run it to see the AssertionError — you can't break anything.

    hello("David") prints hello, David on screen. So does assert hello("David") == "hello, David" pass?

    It fails with AssertionError. hello only prints; it has no return, so it hands back None — just like r = square(5) was None in Lecture 0 when square only printed. The check is really assert None == "hello, David", which is False, so the alarm trips. The text you saw on screen was printed as a side effect; it was never returned, and assert can only compare what a function returns.

    Live — supposed to FAIL. hello only PRINTS, so it returns None; the assert compares None to the string. Run it to see the AssertionError.

    Remember: return vs. print, from Lecture 0

    print just shows a value on screen, while return hands it back to your code — and a function with no return hands back None (the no-value object from Lecture 2). This is the exact print-vs-return run you did in Lecture 0 (r = square(5) was None), now biting you: hello("David") only prints, so it returns None, and assert None == "hello, David" is False. To be testable, a function must RETURN its result, not print it.

    The fix is one word. Change print(...) to return an f-string, so hello hands its greeting back and the asserts have a real string to compare against. Predict: silence from both asserts, then passed. Run it:

    Live — fixed: hello now RETURNS the string, so it's testable. Both asserts pass silently; the final print proves we reached the end.

    A function greet(name) does print(f"hi {name}") AND ends with return name. You write assert greet("Sam") == "hi Sam". What happens?

    assert compares only what a function returns. greet prints hi Sam but returns "Sam", so the check is "Sam" == "hi Sam" — False — and it raises an AssertionError. A function having a return isn't enough; it must return the value you're testing. The printed text is a side effect that never comes back into your code.

    Organizing tests into a folder

    Now that hello.py returns its greeting, it's testable — so let's give its tests a home. As a project grows, you don't want test files cluttered among your real code; you tuck them into a test/ folder. Make it with mkdir test, drop your test_*.py files inside, and add an empty test/__init__.py, which marks the folder as a Python package. Then point pytest at the folder with pytest test.

    Terminal only — the commands

    In your terminal: mkdir test to make the folder, create test/test_hello.py (below) and an empty test/__init__.py (literally nothing in it), then run pytest test. pytest finds every test_*.py by filename whether or not __init__.py exists — the empty __init__.py marks test/ as a package, which keeps test module names from colliding across folders in larger suites.

    Terminal only — save as test/test_hello.py. Imports the returning hello from your hello.py.

    from hello import hello


def test_default():
    assert hello() == "hello, world"


def test_argument():
    assert hello("David") == "hello, David"

    Terminal only — save as test/__init__.py. EMPTY on purpose: it marks test/ as a package. Then run: pytest test

    # (intentionally empty — this file marks test/ as a package)

    And that loops back to where we started. The whole reason we drilled one tiny square is that the moves scale: in a real project with dozens of functions across many files, one command — pytest test — runs every test_ in every file and reports each pass and failure at once. That 1-line check versus eyeballing everything by hand is the entire point of writing tests.

    You create test/__init__.py and leave it completely empty. Is that a mistake?

    An empty __init__.py is a deliberate marker that says "this folder is a package." It's meant to be empty — it holds no tests and isn't a forgotten scratch file. Note that pytest test discovers every test_*.py by filename regardless of __init__.py; the package marker just keeps module names from colliding in larger suites.

    Common mistakes at a glance

    • assert is a statement, not a function call. Write assert CONDITION (optionally assert CONDITION, "message"), never assert(CONDITION, "message") — those parentheses build a two-item tuple, which is always truthy, so the test passes while checking nothing (modern Python warns SyntaxWarning: assertion is always true, perhaps remove parentheses?).
    • A passing test is silent. A True assert produces no output; "nothing happened" means it passed, not that it failed to run. A trailing print is your only proof execution reached the end.
    • A failing assert raises an AssertionError and halts — it does not return or print False. It's an exception, the same raise-and-stop you met with ValueError in Lecture 3. A tripped test is the test earning its keep, not your fault.
    • One passing test can hide a bug. A broken square returning n + n still passes square(2) == 4 and square(0) == 0 — 0 and 2 are the only numbers where n + n equals n n. It fails on square(3), square(-2), square(-3). Always test more than one value — positive, negative, and* zero.
    • A plain chain of asserts stops at the first failure. To report more by hand you wrap each in try/except AssertionError — which works but is verbose. pytest gives that report-everything behavior for free by running each test_ function independently (one red F apiece).
    • pytest is third-party (pip) and runs from the terminal, never the browser. pip install pytest once, then pytest test_file.py. (assert and try/except, by contrast, are built in and run live.)
    • pytest only runs test_-named functions in files named test_.py. A mis-prefixed function (check_square) is silently never run* — no error, just missing coverage. When a test seems ignored, check the prefix first.
    • A print-only function returns None and can't be asserted. assert hello("David") == "hello, David" fails when hello only prints, because it returns None (exactly like r = square(5) in Lecture 0). And a function that does return must return the value you're testing, not just any value.
    • square("cat") raises a TypeError — it evaluates "cat" "cat", and Python won't multiply a string by another string (string int repeats: "cat" 3 is "catcatcat"; string string raises). Test error paths with pytest.raises(TypeError) (terminal) or try/except TypeError (live), and put only the failing call inside the with block.
    • assert is for development/testing, not input validation — use it to catch your own bugs while coding, and use try/except (Lecture 3) to handle what a user types. (Aside, beyond this lecture: under python -O, asserts are stripped entirely, so never rely on one to check user input.)
    • An empty test/__init__.py is on purpose — it marks the folder as a package; pytest discovers every test_*.py by filename whether or not it exists. It is not a mistake or a file to delete.

    Recap & next step

    The big idea is the tripwire: an assert is a wire strung across a fact you believe is true. Step over it cleanly (True) and it's silent — that silence is the test passing, which is why a final print is your proof you reached the end. Trip it (False) and it raises an AssertionError that halts the program — the same raise-and-stop you met in Lecture 3, where int("cat") raised a ValueError. A tripped wire isn't your code failing in a new way; it's the test earning its keep. That one behavior is the engine behind every testing tool.

    From the start you keep your code in one file (calculator.py) and your tests in a separate one (test_calculator.py) that borrows the function with from calculator import square — the same from ... import move as Lecture 4. The progression: start with the clumsy if/print check, replace it with a one-word assert on square(n), and learn that one passing case (square(2)) can hide a bug a second case (square(3)) catches — because n + n equals n n only at 0 and 2 — so test more than one value. A plain chain of asserts halts at the first failure, so you report more failures by hand with try/except AssertionError — it works but is verbose, and that verbosity is exactly what pytest removes: third-party like Lecture 4's pip packages, so terminal only, it runs each test_ function independently and reports every failure for free. pytest.raises(TypeError) tests the error path (square("cat") is "cat" "cat", a TypeError — string times string, not string times int), the professional twin of Lecture 3's try/except.

    The key lesson ties it all together: a function must return, not print, to be testable — a print-only function returns None (just like r = square(5) in Lecture 0), so assert hello("David") == "hello, David" fails until you return an f-string. Once hello returns, its tests live in a test/ folder with an empty __init__.py that marks it a package, and pytest test runs every test in every file at once — the payoff that makes the one-function square drill worth it.
