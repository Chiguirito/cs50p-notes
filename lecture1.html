    Lecture 1 — Conditionals

    Teaching your program to make decisions: ask a yes/no question, branch with if / elif / else, combine tests with and / or, and write a function that hands back a True/False answer.

    What you'll be able to do

    • Write comparisons (<, <=, >, >=, ==, !=) and know each one hands back a real True/False
    • Write a plain if, then a two-way if/else, indenting the block under the colon
    • Chain branches with elif/else — and explain why a row of separate ifs can double-fire while a chain is one fork that runs only the FIRST match
    • Combine conditions with and/or, chain comparisons like 90 <= score <= 100, and dodge the or truthiness trap (if x == 1 or 2)
    • Use % to test parity and write a function that returns a bool — the Pythonic return n % 2 == 0

    Comparisons: questions that answer True or False

    So far a program runs every line, top to bottom. Conditionals let it choose: do something only if something is true. That "something" is a comparison — a yes/no question about two values. The very next cell needs only two of them: < (less than) and == (is equal to, two equals signs). Run this and watch the type that comes back:

    A comparison produces a value you can store — its type is bool.

    A comparison isn't just decoration — it evaluates to a real value: either True or False. That value has a type, bool, and you can store it, print it, and pass it around just like a number or string. Python has six comparison operators in all — here's the full set as a reference to glance back at (you only need < and == for the next cell):

    • < — less than — 3 < 5
    • <= — less than or equal to — 5 <= 5
    • > — greater than — 7 > 2
    • >= — greater than or equal to — 4 >= 4
    • == — is equal to (two equals signs!) — 5 == 5
    • != — is not equal to — 7 != 8
    One = or two? (the #1 beginner bug)

    You met = in Lecture 0 as the assignment operator: it stores the value on the right into the name on the left — not algebra. == is its question-asking partner: it compares two values and answers True/False. So x = 5 puts 5 into x, while x == 5 asks "is x equal to 5?". Read == out loud as "is equal to?". Writing if x = 5: is a SyntaxError (Python catches you), but training your eye on == is what really prevents the bug — when a comparison looks wrong, count your equals signs.

    What does 7 != 7 evaluate to, and what type is it?

    != means "not equal". 7 is equal to 7, so "not equal" is False. Every comparison hands back a real bool (True/False), never a number — that fact powers the rest of this lecture.

    The if statement

    An if runs an indented block of code only when its condition is True. The line ends with a colon, and the body is indented (4 spaces) — the same colon-and-indent shape as def from Lecture 0. That indentation is how Python knows what's "inside" the if.

    Here's compare.py. It opens with the int(input(...)) shape you met in Lecture 0 for reading numbers from the user — the only new part is the if.

    compare.py — your first live input cell. Try x=2, y=3 (prints), then run it again with x=3, y=2 (prints nothing). Tip: break things on purpose, then re-type the fix in your own editor and run python file.py — that muscle memory matters.

    With x = 2, y = 3 you'll see the message. Run it again with x = 3, y = 2 and you'll see nothing — the condition was False, so Python skipped the indented line entirely.

    Beyond the lecture · input() always returns text

    input() hands back a str. If you drop the int(...) and compare the raw text, Python compares it character by character, left to right, by Unicode code-point value — not by numeric size — so '10' < '9' is actually True, because the character '1' sorts before '9'.     Control flow: separate ifs vs. elif vs. else

    compare.py handles one case. Before we add more, look at what happens when you simply stack independent ifs — and pick conditions that can overlap. At score = 95, both of these are true. Run it and count the lines:

    Two separate ifs with OVERLAPPING conditions — both fire. Watch TWO lines print.

    Two lines printed. That's the catch with separate ifs: each is asked independently, every run, with no link between them — so when conditions overlap, several fire at once. The fix is elif ("else if"): it chains the tests so Python stops at the first true one and skips the rest. (For the </>/== case in compare.py the conditions can't overlap, so separate ifs only waste a little work there — but the habit of chaining is what keeps overlap bugs away.) Going back to compare.py with all three cases:

    if / elif / else — Python stops at the first match.

    Notice the final else instead of a third elif x == y:. Once x isn't less than y and isn't greater than y, it must be equal — so else (the catch-all) is both shorter and impossible to get wrong. Use else whenever the last branch is "everything that's left."

    Mental model — the idea to hold onto

    Hold these two pictures side by side. A stack of separate ifs and an if/elif/else chain look almost identical but behave very differently — and the difference is which branches run.

    if / elif / else = one fork in the road
    if x < y:    'less'
elif x > y:  'greater'
else:        'equal'
    You hit the forks one at a time and take the FIRST open road — then never see the others. Python stops at the first True. Exactly ONE branch runs.
    separate ifs = a row of gates
    if score >= 90: 'A-range'
if score >= 60: 'passing'
    Every gate is checked on its own, every run. If conditions overlap (95 clears both), several open at once — as you just saw. There is no link between them.
    Coming from C or Java? (optional)

    It's elif, not else if. Blocks are defined by indentation, not braces {} (and no semicolons). And Python uses the words and/or (which you'll meet next) — never && or ||.

    The or operator

    or joins two conditions and is True when at least one side is true. Look back at compare.py: "less than OR greater than" is just a wordy way of saying "not equal." So or lets us collapse two of its branches into one:

    or is True when at least one side is true. Try x=2,y=3 and x=5,y=5.

    Repeat the comparison on each side of or

    You must write the variable again on each side: x < y or x > y. The tempting shorthand for "is the day Sat or Sun" — if day == "Sat" or "Sun": — is a silent bug: it has no error, but it fires for every value, not just Sat and Sun. Why? The bare "Sun" on the right is a non-empty string, and Python treats that as True — so the whole condition is always true. (That "a value counts as True" idea is truthiness; the section just below makes it concrete.) The rule for now: put a full comparison on both sides of or — day == "Sat" or day == "Sun".

    Beyond the lecture · sometimes or is overkill

    or shines for "is it one of these?", but don't reach for it when a single comparison says the same thing. "less than OR greater than" is exactly "not equal," so the if x < y or x > y: above is even cleaner as if x != y:. Prefer the shortest form that reads clearly.

    Beyond the lecture · why that or bug happens: truthy & falsy

    Beyond the lecture · these notes add this

    Truthiness isn't in CS50's Lecture 1 — it's a robustness idea these notes add to explain the silent or bug you just met. Read it now while that bug is fresh.

    Outside of comparisons, Python treats some plain values as stand-ins for True/False: any non-empty string and any non-zero number count as True; an empty string "" and 0 count as False. Python calls these truthy and falsy. Run this to see it directly — note the last line, the classic trap:

    Truthiness made concrete — this is what if sees when a non-bool sits in a condition.

    That's why if day == "Sat" or "Sun": always fires: the bare "Sun" on the right is a non-empty string, so it's truthy, which makes the whole condition true no matter what day is. Watch the broken and fixed versions side by side:

    BROKEN vs FIXED — bare "Sun" is truthy, so the broken version fires for any day.

    Predict: what does print(bool("0")) show — and how does that differ from print(bool(0))?

    bool("0") is True; bool(0) is False. The string "0" is a character, not the number zero — and any non-empty string is truthy, so its content doesn't matter. Only the empty string "" is falsy. The number 0 is the falsy one. This is exactly why a bare value sneaks past or.

    Which condition correctly checks whether n is 0 or 5?

    or joins two complete questions, so you must write n == on both sides. n == 0 or 5 leaves a bare 5 — which is truthy — so the whole thing is always true (a silent bug). n == "0" compares against the string "0", which never equals the number 0. And if n = 0 uses assignment = inside an if, a SyntaxError.

    The and operator

    and is True only when both sides are true. It's perfect for "is this value inside a range?" — you bound it from below and from above. An A grade is at least 90 and at most 100, so one band looks like this:

    One bounded check with and — both sides must be true. Try score=95, then 105.

    With and, a 95 prints "Grade: A" (it clears both sides) but a 105 doesn't (it fails score <= 100). Now stack a band per grade into grade.py. Each band is written the same way — >= low and < high — except the very top, which caps at <= 100:

    grade.py — enter a score like 85. Every band uses the same >= low and < high shape.

    The A band uses <= 100 (not < 90) only because 100 is the top of the scale — there's no higher band to hand off to. Every band below it uses strict < high so the boundary score lands in exactly one band: an 80 is a B, not a C.

    Beyond the lecture · short-circuit

    and and or stop evaluating as soon as the answer is decided: and stops at the first false side, or stops at the first true side — so the second side might never run. That's handy when the right side is slow or could error. (You've now used both operators, so this trick applies to either one.)

    Chaining comparisons

    score >= 90 and score <= 100 is so common that Python lets you write it the way you'd write it on paper: 90 <= score <= 100. It means exactly "score is between 90 and 100, inclusive," and the value of score is computed once and reused for both comparisons.

    The Pythonic chained form reads like math. Edit score and re-run.

    What a chain means

    90 <= score <= 100 is expanded by Python into 90 <= score and score <= 100 — with score evaluated a single time and reused for both comparisons. (So score still takes part in two comparisons; it's just computed once.) This reads naturally, but most other languages can't do it, so it's a distinctly Pythonic move. When in doubt, the explicit and form always works too.

    What is 90 <= score <= 100 shorthand for?

    Python expands a chained comparison into an and of the neighboring pairs, computing score once and reusing it. The (90 <= score) <= 100 reading is what most other languages would do — Python doesn't.

    Now a cleaner idea for grade.py. Because elif is checked top-to-bottom and only reaches a rung once all the ones above it failed, you can drop the upper bounds entirely — just list the cutoffs highest first:

    The clean one-sided ladder — each elif only fires because the higher ones failed.

    The one-sided ladder only works because the order is right. Flip it so the loosest cutoff comes first and watch a 95 grab the wrong grade — the >= 60 rung swallows everything 60 and up, so A becomes unreachable:

    ANTI-EXAMPLE — inverted ladder. A 95 should be an A. (Same else as the correct one — the ONLY change is the cutoff order.)

    Predict: in that inverted ladder, what grade does a 95 print — and what is the smallest change that fixes it?

    Grade: D. Python checks the first rung, score >= 60, which is true for 95, so it prints "D" and stops — the >= 90 rung lower down is never reached. The first matching rung wins, so the fix is to reorder the rungs highest cutoff first (>= 90, then >= 80, …); no condition needs to change, only their order.

    Beyond the lecture · this assumes a valid 0–100 score

    Dropping the upper bounds is a clean refactor only for in-range input. Bounded grade.py gives a 105 an F (it fails >= 90 and score <= 100 and falls to else), while the one-sided ladder gives a 105 an A (105 >= 90). For real input you'd guard first — if score > 100 or score < 0: print("Invalid") — but for a known 0–100 score the two ladders agree.

    Modulo % and parity (parity.py)

    Remember from Lecture 0

    % is the remainder operator from Lecture 0's operators cell — 7 % 2 is 1. A number is even exactly when its remainder after dividing by 2 is 0, i.e. x % 2 == 0.

    parity.py — enter any whole number.

    Look closely at what parity.py does: it asks the comparison x % 2 == 0, gets back a True/False, and acts on it. That's a tidy little decision — but it's locked inside this one script. What if a function could hand that True/False back to us, so any program could ask "is this even?" The next section does exactly that.

    Functions that return a bool

    In Lecture 0, square(n) handed a value back to your code via return. A function can return any value — and True/False are values too. So we can refactor parity.py into a function is_even(n) that hands back a bool.

    parity.py, refactored: is_even returns a bool. main() defined first, called last.

    Here we define main() first and call it at the bottom — a tidy habit worth keeping as programs grow. And notice if is_even(x): — no == True needed, because is_even already returns a bool, which is exactly what if wants. The function hands back a value; the if consumes it.

    Pythonic boolean return

    That is_even works, but look closely: we test n % 2 == 0 (which is already True or False) and then hand back True or False based on it. A first tightening uses a conditional expression ("X if condition else Y") to fold the four lines into one return:

    Step toward Pythonic: a conditional expression on one line.

    But that's still circular — we test something that's already a bool, then rebuild a bool from it. Since a comparison already evaluates to a bool, we can just return it directly:

    The Pythonic form — return the comparison itself.

    A comparison IS a bool

    Wrapping n % 2 == 0 in if … return True else return False (or True if … else False) is like answering "is it raining?" with "if it is raining, then yes, otherwise no." The comparison is the answer. Just return it.

    Why is return n % 2 == 0 preferred over the version that returns True/False?

    A comparison evaluates to True/False by itself. Returning it directly is shorter and clearer — there's no need to convert a bool into a bool.

    Branching on a value: match / case

    Just like Lecture 0's greeter that printed hello, NAME, we read a name with input() — but this time we branch on it, sorting Harry Potter characters into houses. First, with tools you already have: an if/elif chain, using the or grouping from earlier to gather the Gryffindors:

    Houses with if/elif and or — type Harry, Draco, or anything else.

    When you're matching one value against several fixed options, match/case reads more cleanly — and unlike or, it scales to many options without repeating the variable each time. The variable goes after match, each case lists a value to compare against, and case _ is the catch-all default (like else). Combine alternatives in one case with the pipe | (read it as "or") — the direct parallel of the or grouping you just wrote. match checks cases top-to-bottom, runs the first match, and stops:

    match/case — | combines alternatives, case _ is the default.

    That reads more cleanly than the if/elif chain, especially as the number of cases grows — each option is one short line and the variable name appears only once. (You can also write each value on its own case line without the pipe, but grouping with | keeps related options together.) Unlike switch in C or Java, match has no fall-through: it runs only the first matching case, then exits. There's also a subtler "capture" behavior with bare names you'll meet much later — for now, always match against a literal like case "Harry":.

    Heads up · match needs Python 3.10+

    match/case was added in Python 3.10, and scales nicely once you have many fixed options. It runs in these browser cells (Python 3.12), but on an older local Python — including the 3.9 that ships on many machines — python file.py raises a SyntaxError. For just two or three values, the if/elif/else version above reads fine and runs everywhere; check your version with python --version if match errors.

    Predict: with the match cell above, you run it and type "harry" (lowercase). What prints?

    Who? — the cases test for the exact string "Harry" with a capital H, and "harry" doesn't equal it. So none of the literal cases match and it falls to the wildcard case _:. Comparisons are case-sensitive; match compares values exactly, just like ==. Up next is Problem Set 1, where you'll wire these branches into real problems.

    Common mistakes at a glance

    • = assigns, == compares. if x = 5: is a SyntaxError — read == as "is equal to?" and count your equals signs when a test looks wrong.
    • A comparison evaluates to a real bool (True/False) — you can store it and return it directly. Don't wrap it in if … return True else return False (or True if … else False).
    • Separate ifs are a row of gates — all get checked, and overlapping conditions can open more than one (a 95 clears both >= 90 and >= 60). if/elif/else is one fork in the road that stops at the first true branch. Use elif when you want exactly one.
    • In an elif ladder, order matters: put the highest cutoff first, or a loose rung like score >= 60 matches a 95 first and makes A unreachable.
    • if x == 1 or 2: runs for every x — a bare 2 is truthy (non-zero), so the condition is always truthy. Repeat the comparison: if x == 1 or x == 2:. Same trap with strings: name == "Harry" or "Ron".
    • Truthy/falsy: any non-zero number and any non-empty string act as True in a condition — even "0"! Only 0 and "" act as False. That's why a bare value sneaks past or.
    • input() returns a str. Convert with int() before comparing numbers, or '10' < '9' comes out True (text compares character by character, left to right, by Unicode code-point value).
    • Dropping the upper bounds in a one-sided ladder assumes valid 0–100 input — a 105 prints A there but F in bounded grade.py. Guard the range first if input could be out of bounds.
    • match/case needs Python 3.10+. It works in the browser cells (Python 3.12) but raises a SyntaxError on an older local Python (e.g. 3.9) — fall back to if/elif/else (check with python --version). match has no fall-through and case _: is the catch-all (like else).
