    Lecture 8 — Object-Oriented Programming

    A dict can hold a student's name and house, but it can't check the house is real or do anything with it. A class is your own type that bundles data with behavior — and can refuse to exist in a bad state. This lecture builds one Student class, one feature at a time.

    What you'll be able to do

    • Define your own type with class Student: and an __init__ constructor that runs automatically at Student("Harry", "Gryffindor"), storing data on self and reading it back with student.name
    • Reject bad data at creation with raise ValueError(...) (the same raise from Lecture 3), and give your object a readable print() with __str__
    • Add behavior with instance methods, and guard an attribute with @property + a setter so every write is validated
    • Put behavior on the class with a @classmethod — a factory like Student.get() that returns cls(...), or shared behavior like Hat.sort("Harry") over a class variable
    • Reuse code with inheritance (class Student(Wizard): + super().__init__(...)) and teach operators your types with __add__
    How to run these boxes

    White box, Run button = real Python, runs right here. Edit it, press Run (or Cmd/Ctrl + Enter); Esc steps back out. The first run downloads Python once (about 10 seconds), then it's instant — you can't break anything, so change a line and re-Run freely. Every box below hard-codes its values (e.g. Student("Harry", "Gryffindor")) so you can predict the output before you Run, and each box is self-contained — it defines its class and uses it, so you never scroll up.

    You've used classes all along

    Before we build anything, lower the stakes: a class is not new machinery bolted onto Python — it is Python. You've been making objects since the very beginning: every "text" is a str object and every number an int (from Lecture 0), every [] a list and every {} a dict (from Lecture 2). Ask type(...) and you'll see the blueprint each one came from. And the methods you already call — str.lower(), list.append(), dict.get() — are exactly the instance methods of those classes, reached with the same dot syntax. Predict the four type(...) lines.

    Run it — int, str, list, dict are all classes; their methods are the instance methods you already call.

    So building a class isn't learning a new language — it's learning to make your own type that behaves like the built-in ones. With that comfort, let's see why you'd want one.

    Why classes? A dict gets you close, then stops

    Picture one student — a name and a house — bundled two ways. First a tuple (think of the a, b = ... unpacking you did in Lecture 6 on line.rstrip().split(",") — that split returns a list, but the unpacking move is identical): ordered, but immutable and addressed by position, easy to get backwards. The last line tries to change it. Predict whether it works.

    Run it — a tuple is positional AND immutable. student[0] is the name only because you remember it is. The last line tries to change a value.

    A list is the same shape but mutable — you can reassign student[1] — yet it's still positional and order-fragile: nothing stops you putting the name where the house goes. Watch the third line silently mix them up.

    Run it — a list is mutable but still positional. The third line swaps the two values, and nothing complains — the name is now in the house slot.

    The real upgrade is the dict (the keyed collection from Lecture 2), which gives every value a name — student["name"] says what it means. But watch the last line carefully before you predict.

    Predict the LAST line: student.get("hous") is a typo'd key. Does it error, or print something? (The first f-string just reads two values.)

    The dict is the best of the three — but two gaps remain

    A list reaches a value by position, a dict by key — and the dict is the closest we got to bundling a student. But two gaps remain. Gap one: nothing checks the values. You could store house = "Hogwarts" (not a real house) and the dict shrugs — just as the typo'd student.get("hous") slid through and returned None instead of complaining. Gap two: a dict carries no behavior — it holds data but can't do anything. A class closes both: it can validate itself when created and it can carry its own methods. That's the whole lecture — one Student class, one feature at a time.

    class, __init__, and self: your own type

    You can declare a new kind of thing in one line: class Student:. The simplest version is empty — you then attach name and house from outside, one assignment at a time. This works, but watch how loose it is: nothing forces a student to have a name, and nothing stops a fake house. (CS50 sets these from input(...) here; we hard-code them.) Predict the lines.

    Run it — a bare class, attributes set from OUTSIDE. It works, but nothing is required and nothing is checked.

    That's tedious and unsafe. The fix is the constructor: def __init__(self, name, house): runs automatically the moment you write Student("Harry", "Gryffindor"). Its job is to take the arguments ((self, name, house) takes parameters just like a def square(n) would) and store them on self — the particular object being built. Afterwards you read those values back with dot notation: student.name. Predict the two lines.

    Run it — __init__ runs at Student(...) and sets up the object in one step. self is THIS object being built.

    Recall this class Student with __init__(self, name, house). Stamp out two: s1 = Student("Harry", "Gryffindor") and s2 = Student("Draco", "Slytherin"). After s2.house = "Ravenclaw", what does print(s1.house, s2.house) show?

    It prints Gryffindor Ravenclaw. Each Student(...) call stamped out a separate object with its own self, so s1 and s2 carry independent house values — changing s2 leaves s1 untouched. One blueprint, many independent objects.

    The __ marks a dunder — a hook Python calls for you

    The double underscores in __init__ mark it as a dunder (double-underscore) method: a hook Python calls for you automatically — here, the instant you write Student(...). You never call __init__ yourself, and it returns nothing — its only job is to set up self. You'll meet more dunders below — __str__ for printing, then __add__ for + — but the idea is always the same: you define the method, Python decides when to fire it.

    Mental model — blueprint vs. object vs. self

    Three words people mix up — keep these apart and the rest of the lecture is easy:

    class = the blueprint (one mold)
    class Student: ...
    Written once. It describes the shape every student will have, but it is not a student itself — it's the cookie-cutter. Nothing exists yet.
    instance = one object (a stamping)
    student = Student("Harry", "Gryffindor")
    This presses out one cookie. Student(...) calls __init__ automatically. Stamp as many as you like — each is a separate object with its own name and house (just like s1/s2 above).
    the dot picks the objectYou already saw student.name read off one object, and "HI".lower() work on the string to the left of the dot. The thing on the left of the dot is the object being worked on — and inside a method (coming soon), Python hands you that object as self.

    __str__: a readable print()

    Most boxes from here on print a student, so give it a readable face. Try to print a student now and Python has no idea what you'd want to see, so it falls back to an ugly <__main__.Student object at 0x...>.     Instance methods: giving objects behavior

    Now close gap two: a class can carry behavior. A method is just a def inside the class whose first parameter is self, so it can read that object's data. Start with the simplest possible one — greet() just reads self.name and self.house back out. You call it on the instance: student.greet(). Predict the printed line.

    Run it — the simplest instance method. greet() reads self.name and self.house. You call it on the object: student.greet().

    `self` is a parameter, not a keyword — and you never pass it

    self is not a special word you must memorize — it's just the conventional name for the first parameter, which Python fills in automatically with this object. When you write student.greet(), that's secretly Student.greet(student): the thing on the left of the dot becomes self. Two consequences: every method lists self first, and inside a method you must write self.name to reach the object's data — a bare name is just a local variable that vanishes when the method ends.

    Now a richer method. Give a student a patronus (CS50 carries it on the same Student), and let charm() return an emoji using Lecture 1's match. Predict which case runs for "Stag", then Run to see the emoji. Try changing the patronus to "Otter".

    Run it — charm() reads self.patronus and matches on it. The new attribute patronus is set in __init__ alongside name and house. Try patronus = "Otter".

    Recall: match runs the first case (L1)

    match self.patronus is the match/case from Lecture 1 — it checks cases top-to-bottom, runs the first match with no fall-through, and case _ is the catch-all default. The only new twist: the value being matched lives on self. (CS50 returns literal emoji here; Stag maps to a horse, a well-known quirk. The \U0001F434 form is just a portable way to write that emoji by its code — the output is identical.)

    Heads up — match needs Python 3.10+

    These cells run Python 3.12, so match/case works here. But on the Python 3.9 that ships on many Macs it raises a SyntaxError — on your own machine, write charm() with if/elif/else instead (check your version with python --version).

    Suppose you wrote def charm(): — forgetting the self parameter — and then called student.charm(). What happens?

    student.charm() is always rewritten to Student.charm(student) — Python passes the object on the left of the dot as the first argument no matter what. If your def lists zero parameters, that auto-passed instance has nowhere to land, so you get a TypeError reporting that charm() takes 0 positional arguments but 1 was given. That's the flip side of 'you never pass self yourself': Python always tries to, so the method must declare it.

    @property and @x.setter: validation that can't be skipped

    The raise in __init__ guarded creation — but does it guard everything? Predict before reading on.

    Suppose Student.__init__ validates the house and you build a valid student = Student("Harry", "Gryffindor"). Then you write student.house = "Hogwarts" after creation (with house as a plain attribute). Is that rejected?

    No. The raise in __init__ only runs at creation. A later plain assignment student.house = "Hogwarts" writes straight to the attribute and skips the check entirely, leaving the object in a bad state. That hole is exactly what a property + setter closes: it routes every write — at creation and after — through the same validation.

    The fix is a property. First, the syntax: a line starting with @ is a decorator — a label attached to the def right below it that changes how that method behaves. Put @property above a method named house and reading student.house (no parentheses) secretly runs that method — the getter. Pair it with @house.setter (note: the property's name, not @property again) and Python runs that every time someone assigns to student.house. Now the validation lives in one place and fires on creation and every later write.

    Read this BEFORE the cell — __init__ goes through the setter too

    The most important line in the next cell is self.house = house inside __init__. Trace it in four steps:

    1. house is now a property, not a plain attribute. 2. So self.house = house is an assignment to a property — that runs the setter. 3. The setter validates, then stores the real value in _house (a different name — see the next callout). 4. Later, reading student.house runs the getter, which returns _house.

    So creation and every later write go through the same gate — you write the if house not in [...] check once, in the setter, and __init__ reuses it for free. CS50 guards both fields this way, so the cell makes name a property too.

    Run it — name AND house are now properties, each with a getter and a validating setter. The self.name/self.house lines in __init__ run those setters, so validation lives in one place.

    Why _house and not house inside the setter?

    The property is named house. If the setter wrote self.house = house, it would call itself — an infinite RecursionError, a trap people hit within minutes of writing their first setter. So the actual value is stashed under a different name, _house, and the getter reads it back. The leading underscore is a Python convention meaning 'internal; reach me through the property' — a polite sign, not a lock (student._house = "X" still works). One more thing worth knowing: a property with a getter but no setter is read-only — assigning to it raises an AttributeError, since there's no setter to receive the write.

    Supposed to raise — validation can't be bypassed (our demo of the gap you predicted)

    The next box creates a valid student, then tries to sneak in student.house = "Hogwarts" after creation — the exact hole you predicted earlier. Because house is now a property, that assignment runs the setter, which raises ValueError. Run it, see the error, then change "Hogwarts" to a real house.

    Supposed to raise — assigning a fake house AFTER creation still goes through the setter. Run to see ValueError.

    Both gaps are closed — now point the same tools at new jobs

    Gap one (no validation) is shut by raise in __init__ and, more thoroughly, by the property setters that guard every write; gap two (no behavior) is shut by instance methods like charm(). And you needed no new language — just methods on self. That same machinery scales up. Next, point it at three new jobs: behavior on the class itself (@classmethod), reusing a parent (inheritance), and teaching + your own meaning (__add__).

    @classmethod: behavior on the class, not an instance

    Sometimes a method belongs to the class itself, not to any one object. The most useful kind is a factory: a method that builds and returns an instance. This is exactly how CS50 replaces its get_student() helper — instead of a loose function, Student.get() lives on the class. Mark it @classmethod; its first parameter is cls (the class — think 'self, but for the class itself'), and it ends in return cls(...). Note cls(...) is the same as Student(...), so it runs __init__ and its validation. You call it on the class: Student.get(). Predict the line it prints.

    Run it — a classmethod as a FACTORY. Student.get() builds an instance with cls(...) and returns it. cls(...) is just Student(...), so __init__ runs.

    A classmethod can also just carry shared behavior with no instance at all. A Sorting Hat doesn't need a particular hat-object to sort a student. The four houses live in a class variable — declared in the class body, shared by everything — read here as cls.houses and picked from with Lecture 4's random.choice. Predict the shape of the line (the house is random).

    Run it — a classmethod called on the class with NO instance. houses is a class variable shared by all. Re-run for a different house.

    Recall: random.choice (L4), called on the class

    random.choice(cls.houses) is Lecture 4's random.choice picking one item from a list — the Sorting Hat made literal. And just as you called random.choice(...) without ever making a random object, you call Hat.sort("Harry") on the class, no instance needed.

    Three kinds of method, side by side

    Keep the trio straight: an instance method takes self and needs an object (student.charm()); a @classmethod takes cls and is called on the class (Student.get() as a factory, or Hat.sort(...) for shared behavior); a @staticmethod takes neither — just a plain function living in the class namespace for organization. CS50 mentions static methods but doesn't lean on them; the takeaway is the contrast — self (one object) vs cls (the class) vs neither.

    If sort were instead a plain instance method, def sort(self, name):, what would Hat.sort("Harry") do?

    Calling on the class with Hat.sort("Harry") passes "Harry" as the first parameter. For an instance method that first slot is self, so self would wrongly become the string "Harry" and name would be left unfilled — a TypeError reporting a missing required argument. @classmethod is exactly what makes the first parameter cls (the class) instead, so calling on the class is correct and no instance is needed. (Python never fabricates a temporary Hat() for you.)

    Inheritance: reuse with class Child(Parent)

    A Student and a Professor are both Wizards — they share a name and the rule that a wizard must have one (the same if not name guard, now lifted into the parent). Rather than copy it, put it in a parent class Wizard, then write class Student(Wizard): and class Professor(Wizard):. A Wizard works on its own too. Each child's __init__ calls super().__init__(name) to run the parent's constructor (which validates and stores name), then adds its own extra (house or subject). Predict the four printed lines.

    Run it — Wizard is the parent and works alone (Albus). Student and Professor inherit; super().__init__(name) runs the parent constructor that validates and stores name.

    In the Student(Wizard) above, suppose you delete the super().__init__(name) line, leaving only self.house = house. You then build student = Student("Harry", "Gryffindor") and run print(student.name). What happens?

    You get an AttributeError — the Student object has no attribute name. Defining Student.__init__ replaces the parent's — so without the super() call, Wizard.__init__ never runs, self.name is never set, and the missing-name check is skipped too. The next box lets you see it fail.

    Supposed to raise — Student.__init__ forgets super().__init__(name), so name is never set. Run to see AttributeError.

    New connection — exceptions are a class hierarchy too

    In Lecture 3 you caught a ValueError with try/except ValueError. Here's something you weren't told then: ValueError is itself a class, and Python's exceptions are arranged by inheritance — ValueError, TypeError, and friends all descend from a common base, Exception. Because except catches a class and its subclasses, except Exception: would catch them all — the same parent/child (IS-A) relationship you built with Student(Wizard). (Python's isinstance(student, Wizard) would confirm that link returns True, though we don't need it here.) So inheritance isn't an exotic OOP feature; it's quietly underneath the error handling you already use.

    Operator overloading: define what + means for your objects

    Adding two Students makes no sense — but adding two bank Vaults does. Same machinery, new running example. Why does + add numbers but join strings (the same + you've used since Lecture 0)? Because each class defines its own __add__. Your custom classes have none — so + simply doesn't work yet. (CS50 jumps straight to the finished Vault; we show the failure first so you see why __add__ is needed.) Predict what the next box does.

    Supposed to raise — a Vault with NO __add__. potter + weasley has no meaning yet. Run to see the TypeError.

    Now teach + what to do. Defining __add__(self, other) makes potter + weasley return a new Vault with the totals — self is the left operand, other is the right. Predict the third printed line.

    Run it — __add__ defines + for Vaults. potter + weasley calls potter.__add__(weasley): self is the left, other is the right.

    Given the Vault above, what is type(potter + weasley) — and does the original potter change?

    type(potter + weasley) is <class '__main__.Vault'> — __add__ builds and returns a brand-new Vault. And potter does not change: __add__ only reads self.galleons etc. and constructs a fresh object, it never assigns back to self. That's the well-behaved pattern for + — return a new value rather than mutating the operands, exactly like 100 + 25 gives you 125 without altering 100.

    Going further — the rest of the dunder family

    Lecture 8 itself defines only three dunders: __init__, __str__, and __add__. But __add__ belongs to a larger family that wires operators to your objects — __eq__ for ==, __lt__ for <, __len__ for len(...), and more — each one defined the same way, after which the operator 'just works'. One sibling worth knowing now, because it pairs with the __str__ you learned: __repr__ is __str__'s developer-facing twin — it's what shows when you print a list of objects, like [student]. If you define only __str__, printing [student] still falls back to the ugly <...object at 0x...>; defining __repr__ fixes that. These are all correct Python but beyond the lecture — file them away and reach for them when a specific need arises.

    Common mistakes at a glance

    • self is a parameter, not a keyword — and you never pass it. student.greet() looks like zero arguments, yet Python rewrites it to Student.greet(student). Forget self in the def and you get a TypeError about the argument count; write a bare name = name instead of self.name = name and the value vanishes into a local, then student.name raises AttributeError.
    • __init__ returns nothing — it configures self. Don't write return self or return self.name in __init__; just assign self.name = name. The object already exists when __init__ runs; Student(...) hands it back for you.
    • Reading an attribute that was never set is an AttributeError, not None. Unlike dict.get("hous") (which returns None), student.hous raises. That's a feature — typos fail loudly instead of silently.
    • Inside a @x.setter, assign to the _backing name, never to self.x. Writing self.house = house in the house setter calls the setter again — infinite RecursionError. Use self._house = house; the getter returns self._house. (The leading underscore is convention, not a lock.)
    • Define the getter with @property, then the setter with @house.setter (the property's name, not @property again). Both methods are named house. With only a getter the attribute is read-only — assigning raises an AttributeError. Validating only in __init__ leaves a hole that routing every write through the setter closes.
    • A class variable is shared by ALL instances. houses = [...] in the class body is one object for the whole class — shared state lives on the class, per-object data goes on self in __init__. Great for constants like the four houses; a trap if you .append to a mutable class variable expecting a per-object copy.
    • @classmethod takes cls, not self, and is called on the class. Student.get() (a factory) returns cls(...) and Hat.sort("Harry") needs no Hat(). Read the class variable as cls.houses, not a hard-coded class name, so subclasses work too.
    • Defining a child __init__ overrides the parent — call super().__init__(...). Otherwise the parent's setup (here, validating and storing name) never runs, and self.name won't exist (AttributeError). Child IS-A parent, but only the constructor you actually call runs.
    • __add__ should return a new object, not mutate self. potter + weasley must build and return a fresh Vault; assigning back to self would make + quietly change its left operand. Without any __add__, + on your objects is a TypeError: unsupported operand type(s).
    • __str__ must return the string, not print it. If you print(...) inside __str__ and return None, then print(student) shows your line and a stray None. Return the text; let the caller print.
    • match/case (used in charm()) needs Python 3.10+. It runs in the browser (3.12) but raises SyntaxError on the 3.9 that ships on many Macs — use if/elif/else there. Everything else in this lecture runs on 3.9.
