    Lecture 9 — Et Cetera

    A toolbox of small polish features that make your Python shorter, safer, and friendlier. CS50 lists them flat; these notes group them to help you remember — first, polish you apply to code you already write; then a run of tools that compute on demand (eager vs lazy).

    What you'll be able to do

    • Reach for a set for distinct, unordered items (.add, set() for empty, sorted() before printing), and build a list, dict, or set in one readable line with a comprehension
    • Manage state cleanly — know that reading a global is fine but reassigning one needs global, trace the UnboundLocalError that follows when you forget, and prefer a small class as the fix
    • Document and polish code with ALL_CAPS constants, type hints (n: int, -> str) that mypy checks but Python ignores at runtime, and triple-quoted docstrings that help() reads
    • Pass arguments fluently: list/dict to spread into a call, args/kwargs to collect inside a def, and argparse for free --help and validation
    • Tell eager from lazy — comprehensions (eager, replayable) versus map, filter, enumerate, and generators (yield, lazy), knowing the iterators are one-shot and compute on demand

    set: a collection with no duplicates

    A set is like a list with two rules: it holds only unique items (add the same thing twice and the second is ignored), and it has no order — no set[0], because there's no "first." Build one empty with set(), then .add(...) freely; duplicates just vanish on their own. That makes it the natural tool for collecting the distinct houses the students belong to. Predict which houses end up in the set.

    Run it — four students, three of them Gryffindor, but the set keeps each house once. Same Hermione/Harry/Ron/Draco list of dicts from Lecture 2, read with student["house"]. We sort before printing.

    The clumsy way to do the same thing is a list plus a membership check before every add — if s["house"] not in houses: houses.append(...). The set makes that check disappear: it enforces uniqueness for you. And because a set has no order, we wrap it in sorted(...) before printing — the everyday way to put any collection in a predictable order (you met sorted in Lecture 6, there with a key=; here the items are plain strings, so no key is needed).

    Empty {} is a dict, not a set

    This trips up everyone once: houses = {} makes an empty dict, not an empty set ( {} is defined as the empty-dict literal; there is no empty-set literal). For an empty set you must write set(). A non-empty set literal like {"Gryffindor", "Slytherin"} is fine — it's only the empty one that's ambiguous. And since a set has no positions, houses[0] raises a TypeError: loop over a set, don't index it.

    You write colors = {"red", "blue", "red"}. What does print(len(colors)) show?

    2. The duplicate "red" collapses, so colors is {"red", "blue"} — length 2. That's the whole point of a set: same item twice, kept once. (Which order the two would print in is unspecified — that's why we sort a set before showing it.)

It works, but it's discouraged: loose shared state is easy to clobber from anywhere.     Why it raises: a 3-step trace

    The error is UnboundLocalError. Trace it in three steps:

    1. balance += n means balance = balance + n — an assignment. 2. An assignment to a name inside a function tells Python "balance is local to this function." 3. But step 1 has to read balance first to add n to it — and the local doesn't exist yet. Reading a not-yet-set local is the UnboundLocalError.

    The one-line fix is to add global balance as the function's first line — then balance means the outer one and the += works. Reading a global with no assignment never hits this; only an assignment makes the name local.

    You write def show(): print(balance) with NO global line, and balance = 100 at the top. Does show() raise an error, or print 100?

    It prints 100. Reading a top-level variable inside a function is always fine — global is only needed to reassign it (see the 3-step trace above). No assignment in the function, no UnboundLocalError.

    global fixes the error, but you already have the cleaner tool. Put the balance on an object and there's no global to trip over.     constants: ALL_CAPS (by convention)

    A constant is a value you don't intend to change — the number of meows, a tax rate, the four houses. Python has no special keyword for this. The convention is to NAME it in ALL_CAPS so any reader knows "don't reassign me." That's a message to humans, not a rule Python enforces. Constants also live nicely on a class (like Lecture 8's class variable), where a method can read them through self. Predict how many meows print.

    ALL_CAPS is a signal, not a lock

    Python will happily let you write MEOWS = 5 on the next line — nothing stops the reassignment, no error. The capital letters are purely a convention that signals intent to other programmers (and future-you). Like the leading underscore you saw in Lecture 8's _house, it's a polite convention, not something Python enforces.

    type hints + mypy: name the types

    A type hint annotates what type a value should be: number: int = 3 says number is an int, and def meow(n: int) -> str: says n is an int and the function returns a str (-> str). Hints are documentation — they make code self-explaining and let editors and a tool called mypy catch type mistakes before you run. But here's the crucial part: Python ignores them at runtime. The annotation is just attached as data; nothing checks it when the program runs. That's why this cell runs live.

    Run it — hints document the types (n: int, -> str) but Python does NOT enforce them at runtime.

    def describe(n: int) -> str: return "got " + str(n). You call describe("hello") — a string, not the int the hint promised, and no mypy involved. Does Python raise a TypeError?

    No — it prints got hello and runs fine. Type hints are not checked at runtime; Python treats them as comments and runs the code regardless. The hint was wrong about the value, and nothing stopped it. That's the whole point of the mypy tool below: hints do nothing on their own, but a separate checker reads them and flags mismatches before you run.

    docstrings: built-in documentation

    A docstring is a triple-quoted string placed as the first line inside a def (or class). It documents what the thing does — and unlike a # comment, it's real data: tools like help(), your editor, and doc generators (Sphinx) read it back out of the function. A short one fits on one line; longer ones describe each parameter and the return value. Predict the two things this prints.

    Run it — the docstring is the first statement under def; help() and __doc__ read it back.

    You put a triple-quoted string as the SECOND statement under def (after a line of real code). Does help() / __doc__ still show it?

    No — __doc__ is None. Only the very first statement under def is captured as the docstring. Placed anywhere else, a triple-quoted string is just an ignored string sitting in the body — Python evaluates it and throws it away. That's the load-bearing rule: docstring = first statement, triple-quoted.

    A docstring is NOT a # comment

    Two rules people miss: (1) it must be the very first statement under the def, before any code; (2) it must be triple-quoted, not a # comment. A # comment is invisible to help(), editors, and Sphinx; only a docstring is stored on the function (as __doc__) and read back by tools. The longer :param / :return form is what documentation generators turn into web pages — but a one-line summary is plenty for now.

    argparse: friendly command-line arguments

    When you run a program from the terminal, you often want to pass options: python meows.py -n 3. The argparse module turns those command-line words into named, validated arguments — and gives you --help for free. (It's the friendly cousin of Lecture 4's sys.argv: argparse handles the conversion and length-checks you'd otherwise do by hand.) You declare each option once; in return you get type checking (type=int), a default (default=1), and an automatic usage screen. It reads the actual command line, which a browser tab doesn't have, so this one is copy-only.

    Terminal only — run argparse from the command line

    Save the next box as meows.py, then in your terminal run:

    python meows.py -n 3 → meows three times python meows.py → meows once (the default=1) python meows.py --help → prints usage info, then exits

    Notice what you get for free: --help, the -n flag, and type=int (which rejects -n cat with a friendly error instead of crashing). That's argparse's payoff over hand-parsing input yourself.

    Copy only — argparse reads the command line. Save as meows.py, then: python meows.py -n 3

    import argparse

parser = argparse.ArgumentParser(description="Meow like a cat")
parser.add_argument("-n", default=1, type=int, help="number of times to meow")
args = parser.parse_args()

for _ in range(args.n):
    print("meow")

    Unpacking: spread a list or dict into a call

    The * and symbols let you spread** a collection back out into a function's arguments at a call:

    • Put * before a list to fill positional slots in order.
    • Put before a dict** to fill them by keyword (its keys must match the parameter names exactly).

    Here's CS50's wizard-coin example: total takes three coins, and we spread a list (then a dict) into it. Predict: do total(*coins_list) and total(**coins_dict) print the same number?

    Run it — *coins spreads a LIST into positional args; **coins spreads a DICT into keyword args (keys must match the parameter names).

    Recall: unpacking a split, from Lecture 6

    Lecture 6 unpacked a CSV line with name, house = line.rstrip().split(",") — naming both pieces with =. coins_list / coins_dict point that same unpacking idea the other way: instead of receiving pieces into names, you spread* a list or dict back into a call's arguments. And Python never spreads automatically — passing the list itself, total(coins_list), sends one** argument (the whole list) where three are expected, a TypeError. The * is what asks for the spread.

    Given def total(galleons, sickles, knuts): ... and coins = [100, 50, 25], what does total(coins) (no *) do?

    Without the , the list is passed as a single argument — so galleons becomes the whole [100, 50, 25] and the other two parameters get nothing, a TypeError for missing arguments. The is what spreads the items into the slots. Python never spreads automatically; you have to ask with * (positional) or ** (keyword).

    *args / **kwargs: collect extra arguments

    At a call, / spread a collection out (last section). In a def, they point the other* way — they collect** leftover arguments in:

    • def f(args, kwargs) — args gathers extra positional arguments into a tuple; kwargs gathers extra keyword arguments into a dict.

    The names args/kwargs are just convention; the */** is what matters. Predict the two printed lines.

    Run it — *args collects extra positionals into a tuple, **kwargs collects extra keywords into a dict.

    Same symbols, opposite direction

    This is the easiest pair to confuse, so anchor it. In a call, list/dict spread a collection out into arguments. In a def, args/kwargs collect leftover arguments in — args is always a tuple, kwargs always a dict, never lists. Same symbols, opposite direction. One ordering rule: kwargs must come last** in the def — putting it before *args is a SyntaxError.

    In def f(*args, **kwargs): ..., after calling f("David", "Malan", house="Gryffindor"), what are the types of args and kwargs?

    args always gathers the extra positional arguments into a tuple — here ("David", "Malan"). kwargs always gathers the extra keyword arguments into a dict — here {"house": "Gryffindor"}, keyed by the keyword name. The names are just convention; the / decide the behavior, and the containers are always tuple/dict, never lists.

    map: apply a function to every item

    map(function, sequence) applies a function to every item in a sequence. CS50's example wraps it in a yell function that upper-cases its words — and yell(words) even reuses the args collect form you just met. Run it and it prints THIS IS CS50. But there's a twist in how map does its work — and that twist is the idea the whole second half turns on. Predict the output, then read the mental model below.

    Run it — yell collects its words with args, then map(str.upper, words) upper-cases each one. spreads them back out to print.

    Mental model — eager list vs lazy iterator

    map didn't build a list — it handed back a lazy iterator, and that one distinction unifies the rest of the lecture (comprehensions, filter, enumerate, generators). The for-loop you already know still drives all of these; what's new is that a lazy iterator computes each value only when asked, and can be walked through only once. One picture all the way through: a printed list you keep versus a roll of tickets you pull through once.

    EAGER = a printed list you keep
    result = []
for s in words:
    result.append(s.upper())
    Every value is computed up front and kept in memory. It's a real list (the comprehension below is the one-line version): you can index it, check its length, and reuse it as many times as you like.
    LAZY = a roll of tickets
    map(str.upper, words)
    Nothing is computed yet. Each value is produced the instant you pull the next ticket — so only one exists at a time. That's why it stays memory-light even for huge or endless streams, and why print(it) shows <map object ...>, not the values.
    The roll runs out ONCEPulling a lazy roll — with list(it), a for, or it (the same you used to spread a list, now pulling every value out of the roll) — empties it. Pull again and you get nothing back. You'll see exactly this in the next cell. To keep the values, print them onto a list: list(map(...)).

    Run it — predict the first line before the second, then watch the SECOND print of the same iterator.

    After the first print(mapped) prints THIS IS CS50, what does the SECOND print(mapped) print?

    This is the one-shot rule, the single most important gotcha in the second half. A map object is a lazy, one-shot ticket roll. The first print(*mapped) pulls every ticket, emptying it; the second finds nothing left and prints an empty line — no error, just silence. If you need the values more than once, keep them: values = list(map(...)), then reuse values freely.

    List comprehensions: the eager one-liner

    You half-know the eager side already — it's the for-loop-with-append from the mental model. A list comprehension is that loop in one readable line: [expression for item in sequence if condition]. Read it left-to-right: take s["name"], for each s in students, but only if the house is Gryffindor. Unlike map's ticket roll, it gives you a real list you can sort and reuse. Predict the three names.

    Run it — one line builds the list of Gryffindor names. The if filters (it comes after the for). A real list, so it's sortable and reusable.

    The filtering `if` goes at the END

    To filter items, the if goes at the end: [s["name"] for s in students if s["house"] == "Gryffindor"] — exactly as in the cell. (There's a second if shape for choosing between two values per item, a ternary that goes at the front — but you won't need it yet; it's in the footer gotchas if you're curious.)

    Dictionary comprehensions: build a dict in one line

    The same one-line idea builds a dict — just write a key: value pair instead of a single expression: {key: value for item in sequence}. CS50's example assigns every student to the same house. Note the colon — that key: value shape is what makes it a dict comprehension rather than a set one. Predict the dict that prints.

    Run it — {student: "Gryffindor" for student in students} pairs each name with a house. The colon makes it a DICT comprehension.

    Colon = dict, no colon = set

    One symbol decides the type inside the braces: {k: v for ...} (with a colon) builds a dict; {expr for ...} (no colon) builds a set. Easy to mix up — and a dict comprehension silently keeps only the last value for any repeated key, the same collapse a plain dict does.

    filter: keep the items that match

    Where a comprehension's if filters inline, filter(predicate, sequence) is the dedicated lazy tool — a predicate is just a function that returns a True/False test. filter keeps only the items for which that test returns True. Like map, it's a one-shot ticket roll, and it keeps matching items — it doesn't transform them. CS50's canonical predicate is a one-line lambda (Lecture 6's no-name function). Note that filter yields the whole dicts, so we read s["name"]. Predict which names survive.

    Run it — filter keeps the students whose lambda returns True. It yields the dicts, so sorted() needs a key= (you can't compare two dicts with <). Lazy + one-shot, like map.

    Recall: the lambda is Lecture 6's no-name function

    lambda s: s["house"] == "Gryffindor" reuses the lambda from Lecture 6 — a def shrunk to one line, the kind you handed to sorted(..., key=lambda s: s["name"]). Here the lambda must return a bool: filter keeps each item where that bool is True and drops the rest. And since filter yields whole dicts, you can't bare-sorted() them — Python can't compare two dicts with < — so the cell passes the same key=lambda s: s["name"] to sort by name. A named function works identically if you prefer one: def is_gryffindor(s): return s["house"] == "Gryffindor".

    enumerate: index AND value in one loop

    When you need both the position and the item in a loop, the clumsy way is for i in range(len(seq)): ... seq[i] — looping over indexes, then indexing back in. enumerate(seq) hands you both at once as (index, value) pairs: for i, student in enumerate(...). It counts from 0, so add 1 for human numbering (or pass start=1). Predict the first printed line.

    Run it — enumerate gives (index, value) pairs. It starts at 0, so we print i + 1; or pass start=1 and let it do the +1.

    Recall: this replaces range(len(...)) from Lecture 2

    In Lecture 2 you numbered items with for i in range(len(students)): print(i + 1, students[i]) — looping over indexes, then indexing back in. enumerate hands you the index and the value together, so that clumsy double step disappears. (Like map and filter, enumerate is technically a one-shot lazy iterator — but you'll almost always consume it in a single for loop, so that rarely bites here.)

    You write for pair in enumerate(["a", "b"]): print(pair) — a SINGLE loop variable, not two. What prints?

    enumerate yields a (index, value) tuple for each item. With two loop variables (for i, name in ...) Python unpacks the tuple for you. With a single variable, that whole tuple lands in pair, so you see (0, 'a') and (1, 'b'). It's not an error — just un-unpacked. (You'd only get an unpack error with the wrong number of variables, like three.)

    Generators (yield): values one at a time

    A generator is the purest form of the lazy idea. CS50 builds it in two steps. First the eager version: a normal function that builds the whole list of sheep up front, then returns it. ("🐑" * 0 is the empty string and range starts at 0, so the first printed line is blank — then one sheep, then two.)

    Run it — the FIRST output line is blank on purpose ("🐑" * 0 == ""), then one sheep, then two. This eager version holds the whole list in memory at once.

    Now the lazy refactor — the move CS50 makes next. Keep the same shape, but use yield instead of building a list: each yield hands back one value and pauses the function, resuming where it left off when you ask for the next. For n = 3 the output is identical (blank line, one sheep, two), but this version holds only one sheep at a time.

    Run it — same output as above (blank, one, two), but yield emits one value per loop, holding only one at a time. n = 3 keeps it finite.

    yield pauses; return exits

    The one-line difference that changes everything: return ends the function and hands back a single value, done. yield hands back a value and pauses, keeping its place so the next request resumes right after it. That's how a generator emits a stream. And like map/filter/enumerate, a generator is one-shot — exhausted after one pass. The payoff is memory: a generator never builds the whole list, so it works for sequences too big (or endless) to fit in memory.

    Both sheep(n) (yield) and sheep_list(n) (builds a list) print the same lines for n = 3. If you needed it to feed an ENDLESS stream of sheep, which one could you use — and why?

    Only the generator (yield). The eager sheep_list would try to append forever and build an infinite list — it never finishes and runs out of memory. The generator holds just one value at a time and produces the next only when asked, so it can feed an endless stream cheaply. That memory-light, on-demand behavior is the whole reason yield exists. (We still hard-code n = 3 in the live cell so it terminates — never write an endless generator behind a bare for s in sheep(): ..., or the loop never ends.)

    Common mistakes at a glance

    • Empty {} is a dict, not a set. Use set() for an empty set ( {} is the empty-dict literal; there is no empty-set literal). A set is also unordered (no set[0] — that's a TypeError) and unique by equality (2 and 2.0 collapse to one item), so sorted() it before printing if you want predictable output.
    • balance += n without global raises UnboundLocalError. The assignment makes the name local, so += tries to read that local before it's set (see the 3-step trace). Reading a global is always fine; only reassigning needs global balance. Better still: put the state on a class (globals are discouraged).
    • ALL_CAPS constants aren't enforced. Python will happily let you reassign MEOWS = 5, no error. The capitals are a signal to humans, not a lock — like the _field underscore from L8, a convention rather than a rule.
    • Type hints are ignored at runtime. def meow(n: int) does not make Python check n; that's mypy's job, run separately in your terminal. Hinted code runs live exactly as if the hints weren't there — Python just stores them in __annotations__.
    • A docstring must be the first statement under def, triple-quoted. Placed second (after any code) it's an ignored string and __doc__ is None. A # comment is invisible to help()/editors/Sphinx; only a docstring is stored on the function and read back by tools.
    • Same symbols, opposite direction. In a call, total(list)/total(dict) spread into arguments; in a def, args/kwargs collect leftovers (a tuple and a dict, never lists). Passing the list itself (total(coins)) is a TypeError, and **kwargs must come last in a def.
    • map/filter/enumerate/generators are lazy AND one-shot. print(mapped) shows <map object ...>, not the values — use print(*mapped) or list(mapped). And once you walk it, it's exhausted: a second pass yields nothing (no error, just silence). Prefer an eager comprehension, or capture with list(...), if you need it twice.
    • filter yields the original items, unchanged. Its predicate (a True/False test, often a lambda) must return a bool; it keeps matches, it doesn't transform them. Since it yields whole dicts, you can't bare-sorted() the result — pass key=....
    • Comprehension if placement matters. A filter if goes at the end ([x for x in xs if cond]). A separate choice form is a ternary that goes at the front ([a if cond else b for x in xs]) — swapping the two is a SyntaxError. And inside braces, {k: v ...} (colon) is a dict while {expr ...} (no colon) is a set.
    • enumerate starts at 0 and yields a (index, value) tuple. Add 1 (or pass start=1) for human numbering; unpack with two loop variables (for i, name in ...), or a single variable catches the whole tuple (0, 'Hermione').
    • yield pauses, return exits. A generator is one-shot like map; keep live demos finite (n = 3) — never write a bare endless for s in sheep(): ..., or the loop never ends.

    Recap & next step

    Big picture: this lecture is a toolbox. CS50 lists its items flat; to make them stick, these notes group them. The first half is polish you apply to code you already write (set, global/class, constants, type hints, docstrings, argparse, unpacking, args/kwargs) — eight independent tools. The second half is a run of tools that compute on demand, sharing one idea: eager vs lazy. A list/dict/set comprehension builds a finished collection up front (eager, replayable); map, filter, enumerate, and generators (yield) compute one value at a time on demand (lazy, memory-light, and one-shot — they print as objects and exhaust after one pass). When in doubt, reach for the eager comprehension; save the lazy tools for huge or endless data.\n\nWhat each piece does:\n- set() + .add(...) — a collection of unique (by equality), unordered items; sorted() before printing.\n- global x — reassign a module-level variable from inside a function (discouraged; prefer a class).\n- NAME in ALL_CAPS — a constant by convention, not enforcement.\n- n: int / -> str — type hints: documentation that mypy checks but Python ignores at runtime.\n- """docstring""" — first statement under def, readable by help().\n- argparse — free --help, defaults, and type validation from the command line.\n- total(list) / total(dict) — spread a collection into a call; def f(args, kwargs) — collect extras into a tuple and dict.\n- map(fn, seq) — apply a function to every item (lazy); wrap in list() or unpack with to see it.\n- [x for x in seq if c] / {k: v for ...} / {x for ...} — build a list, dict, or set in one line (eager).\n- filter(pred, seq) — keep matching items (lazy, one-shot).\n- enumerate(seq) — (index, value) pairs, cleaner than range(len(...)); starts at 0.\n- yield — a generator: values one at a time, even for endless streams.\n\nThis ties back where you've been — the list/dict of L2 (and the range(len(...)) that enumerate replaces), the scope rule and the _field + @property class pattern of L8, the split unpacking and lambda of L6, the sorted you first used in L6, and sys.argv of L4 (whose friendlier cousin is argparse).\n\nNext:** Problem Set 9 — reach for these tools where they fit: a set to dedupe, a comprehension or map/filter to reshape data, enumerate to number it, argparse for a real command-line program, and a class wherever loose globals tempt you.
