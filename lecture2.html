    Lecture 2 — Loops

    Doing something again and again without repeating yourself: count with while, walk a sequence with for and range, ask until the input is good with while True + break, and loop over lists, dicts, and grids.

    What you'll be able to do

    • Write a while loop with all three parts — start, condition, and a step toward the fence — and explain why a missing step loops forever
    • Use for i in range(n) to repeat n times, knowing range(n) gives 0 .. n-1 (so n is the count, not the last value)
    • Validate input with while True + break (and meet continue), then wrap it in a get_number() where return replaces break
    • Store values in a list (reached by position) and a dict (reached by key), loop over each, and test for missing values with is None
    • Nest a loop inside a loop to draw a grid (the inner loop runs fully per outer pass, so size × size), using end="" and a bare print() to control line breaks

    Why loops: the same line, over and over

    In Lectures 0 and 1 a program ran each line once, top to bottom. But programs constantly need to do the same thing several times. Say you want a cat to meow three times. With only the tools so far, you'd write the same line three times — it works, and it's already annoying:

    Three identical lines. It works — but imagine doing this 100 times, or letting the user pick the number.

    Copy-pasting is fine for 3 and miserable for 300 — and if you wanted a different number of meows each run, you couldn't write the lines ahead of time at all. A loop says "do this block again and again" without repeating yourself. This whole lecture is two loops — while and for — and the containers (list, dict) you'll most often loop over.

    The while loop

    A while loop repeats its indented block as long as a condition stays True — the same colon-and-indent shape you've used since if in Lecture 1, except now the block runs again and again. Run this and watch i count 0, 1, 2:

    The idiomatic while loop. i starts at 0, the test i < 3 is checked before each pass, and i += 1 steps it forward. Three meows, then it stops.

    Now the shape. Three pieces make a while loop work, and you need all three: a start value (i = 0), a test checked before every pass (i < 3), and a step in the body that moves i toward making the test False (i += 1). Each full pass is one iteration. With i going 0, 1, 2, the body runs exactly three times; then i is 3, 3 < 3 is False, and the loop ends. The catch: making the test eventually False is your job.

    What is i += 1?

    i += 1 is shorthand for i = i + 1: take i, add 1, store it back. That one line is the step — without it, nothing would move i toward the fence. (+= has matching friends -=, *=, and so on.)

    Leave the step out, and here's what happens — i never changes, the test never goes False, and meow prints with no end. CS50's classic version of this counts down instead: it starts i at 3 and loops while i != 0, but forgets the line that lowers i. So i stays 3 forever. This box has no Run button on purpose:

    Never run this — it loops forever. There is no line that changes i, so i stays 3 and i != 0 stays true with no end. (At a real terminal you'd stop a runaway loop with Ctrl-C; a browser cell can't be interrupted, which is why this one box is locked.)

    # Never run this — it loops forever (nothing changes i, so i stays 3)
i = 3
while i != 0:
    print("meow")
    Mental model — the idea to hold onto

    Almost every while-loop bug comes from ONE idea: a loop is repetition steered by a value that changes each pass, and it ends only when that value crosses a line. The two cells you just saw are the same picture — once working, once broken.

    A counter walking to a fence
    i = 0
while i < 3:
    print('meow')
    i += 1      # <- steps toward the fence
    The condition i < 3 is a FENCE. i starts at 0 and steps toward 3 each pass; the walker keeps going until it reaches the fence, then stops. The step i += 1 is what moves it.
    Forget to step = walk forever
    i = 3
while i != 0:
    print('meow')
    # <- nothing lowers i!
    Same picture, broken: no step toward the fence. i stays 3, so i != 0 is true forever. This is THE infinite loop — and the one box on this page locked from running.
    Predict: after the working i = 0 / while i < 3 loop above finishes, what is the value of i?

    3. The body ran with i equal to 0, 1, and 2 (three meows), then stepped i to 3 — and at that point 3 < 3 is False, so the loop stopped without running the body again. So i lands exactly on the fence, 3.

    You write i = 0 then while i < 3: print("meow") but leave OUT the i += 1 line. What happens?

    Without i += 1, i is stuck at 0 forever, so i < 3 is always True and the loop never ends — the counter has no step toward the fence. This is the same trap as the locked box above (which counts down and forgets to lower i). Every while loop needs a line that moves its condition toward False.
    How CS50 builds up to this (optional)

    The zero-based form (i = 0 / while i < 3: / i += 1) is the one to reach for, and it's where CS50 lands — but the lecture gets there by refining naive versions first: a broken countdown (i = 3 / while i != 0: with no step), then fixing it with i = i - 1, then counting up (i = 1 / while i <= 3: / i += 1). All give three meows; the only rule is that a step must move the counter toward the fence.

    The for loop and range

    A while loop is right when you don't know in advance how many passes you'll need. But "do this exactly 3 times" is so common that Python has a cleaner tool: the for loop. A for loop walks through a sequence of values, one per iteration — no counter to start and no step to remember, so the infinite-loop trap simply can't happen. Here it walks a list of three numbers:

    for binds i to each item in the list, one per pass. The numbers themselves don't matter here — just that there are three.

    When the list runs out, the loop ends on its own. But typing [0, 1, 2] by hand gets old fast (picture [0, 1, 2, …, 99]). range(n) generates that run of numbers for you, starting at 0. So range(3) gives 0, 1, 2 — and the for loop runs once per value:

    range(3) gives 0, 1, 2. Same three meows, far less typing.

    range(n) gives 0 .. n-1 — it never includes n

    range(3) produces 0, 1, 2 — three values, stopping before 3. The number n is how many values you get, not the last one. This is the same fence logic as while i < 3: both give exactly 3 iterations and both stop before using 3. The off-by-one trap is expecting range(3) to include 3.

    Don't take that on faith — print the values range(3) actually hands out and count them. (This little cell isn't part of CS50's cat.py; it's just a quick check.)

    Quick check: range(3) yields 0, 1, 2 — and stops before 3.

    Where each loop leaves its counter

    You just watched range(3) stop at 2 — so after this for loop, i holds 2, the last value actually used. Compare the working while i < 3 loop from earlier, which left i sitting on 3: it took one extra step before the test caught it. The for loop never takes that extra step — it stops the instant the values run out.

    Predict: how many times does for _ in range(0): print("hi") run, and what does it print?

    Zero times — it prints nothing at all. range(0) is an empty run of numbers (it would be "0, 1, … up to but not including 0," which is no numbers), so there's nothing for the loop to walk and the body never runs. A for loop over an empty sequence is perfectly legal; it just does nothing. (And range(5) would print 0, 1, 2, 3, 4 — five values, stopping before 5.)

    In the meow loops we never actually use the loop value — we just want the block to run three times. When a value exists but you won't use it, the convention is to name it _ (a single underscore), an ordinary variable name that quietly signals "I'm ignoring this":

    _ is a normal variable name, used by convention for a value you won't use. Python doesn't treat it specially.

    while True with break

    Now the case for can't handle: repeating until the user gives good input, where you have no idea how many tries that takes. The pattern is while True — a loop whose condition is always True — escaped by a keyword called break, which leaves the loop entirely. Here we read a number with int(input(...)) (the same read-a-number move you used in Lecture 1's compare.py and grade.py): if it's positive we break out; otherwise the loop just goes round and asks again.

    Enter 0 or a negative number first (the loop goes round and re-asks), then a positive one (break leaves the loop). print(n) confirms we captured a good value.

    Notice this loop does end — even though while True has no condition that turns False, the break is reachable the moment you type a positive number. There's a second escape keyword, continue, and it's the surprising one: continue does not leave the loop — it skips the rest of this pass and jumps back to the top to go round again. In this exact validator continue isn't needed (just looping round already re-asks), but it's worth meeting, so here's the same loop written the long way to show both keywords side by side:

    Same result, written to show both keywords: if n is not positive, continue jumps back to the top; otherwise break leaves. This is more verbose than the version above — continue is doing what "just loop round" did for free.

    Once a break hands us a good n, a separate for loop does the meowing:

    The whole program: keep asking until n is positive, then meow n times. Type a positive number.

    while True ends only if a break is reachable

    while True has no condition that turns False, so the only way out is a break (or a return) your code can actually reach. The loops above are safe because a positive number reaches the break. continue does the opposite — it loops again, so on its own it never leaves. Always ask: "what input gets me to the break?"

    These input cells are intentionally live (not locked like the stepless cell earlier): each pass pauses on an input pop-up rather than spinning, so it can never freeze the tab — press Cancel to stop. And if you type letters instead of a number, int() raises a ValueError and the cell stops with an error — just re-run and enter a number. (Handling bad text gracefully comes later.)

    In the while True loops above, which input ever reaches the break and ends the loop?

    The test is if n > 0, so only a positive number reaches the break and leaves. Zero and negatives fail the test, so the loop simply goes round (in the long version, continue makes that explicit). while True ends precisely when a reachable break fires.

    Right now the asking and the meowing live in two loose cells — there's no clean name for either job, and nothing to reuse. Let's package them into functions. Recall the habit from before: in Lecture 0 square() did its work and returned a number; in Lecture 1 is_even() returned a True/False. So get_number() can loop until the input is good and return it. And inside a loop, return does double duty: returning from a function hands back a value and exits the function — which leaves the loop too. So in get_number(), return n replaces the break outright. main() then composes them in one line, defined first and called last (the tidy habit from Lectures 0 and 1):

    cat.py, packaged into functions (CS50's exact shape). Inside get_number(), return n leaves the loop AND hands the value back in one move — no break needed. Enter 0 or a negative first, then a positive number.

    Predict: suppose you replaced return n with a plain break inside get_number(). What would main() receive, and why does that break the program?

    break only exits the loop — it doesn't hand any value back. After the loop ends, get_number() reaches the end of its body and returns None (Python's no-value, coming up next), so meow(get_number()) calls meow(None). Then range(None) raises a TypeError because you can't count to None. That's exactly why return n is the right tool here: it both ends the loop and gives main() the number it asked for, in one move.

    Lists: many values under one name

    Looping is most useful over a collection of things. A list holds several values in order, under one name, written in square brackets. Remember Hermione, Harry, Ron, and Draco from Lecture 1's house-sorting match? Same cast — this time they live in a list. Each item has a position number (an index) starting at 0, and you reach an item with name[index]:

    A list keeps values in order. Indexing starts at 0, so students[0] is the first item.

    Indexing one at a time defeats the point — looping is what lists are for. A for loop over a list hands you each item directly, no index needed. Read for student in students: as "for each student in the students list":

    for-over-a-list gives you each item directly — the cleanest way to visit every value.

    Sometimes you also want the position — say, to number them 1, 2, 3 for a human. len(students) gives the count of items (here, 3), and range(len(students)) gives the valid indices 0, 1, 2 — the same fence as range(3), lined up exactly with the list. Loop over those indices, and add 1 when printing so it reads 1-based for people:

    len() gives the count; range(len(...)) gives the indices. The + 1 makes the numbering start at 1.

    Predict: what does the very first line of that last cell's output look like?

    1 Hermione. On the first pass i is 0, so i + 1 is 1 (the human, 1-based number) and students[0] is "Hermione"; print puts a single space between them by default. Valid indices run 0 … len(students)-1 (here 0, 1, 2), which is exactly what range(len(students)) gives you — so it never runs off the end of the list.

    Dictionaries: looking things up by key

    A list answers "what's at position 2?" But often you want to look something up by a name, not a number — like a real dictionary, where you find a word and get its definition. A dict stores key: value pairs in curly braces. Here each name (the key) maps to a house (the value). You look up by key with students["Hermione"] — a key, not a number:

    A dict maps keys to values. Look up by KEY in brackets: students["Hermione"], not a number.

    Lists use a position; dicts use a key

    With a list, students[0] means "the item at position 0." With this dict, students[0] is an error — there is no key 0, so Python raises a KeyError. A dict is reached by its keys: students["Hermione"], not students[0]. Asking for a key that doesn't exist is also a KeyError. Different container, different access: lists by numeric position, dicts by key.

    Now the part to slow down for. A few blocks ago, for over a list handed you each value directly. Looping a dict does not do the same thing: for student in students: hands you the keys, not the values. (Same container word, opposite behavior — this is the classic dict surprise.) So to print both, use the key you're handed and look up its value with students[student]:

    Iterating a dict gives KEYS. Use students[student] to get each value.

    Looping for student in students: over a dict like {"Harry": "Gryffindor"}, what does student hold each pass?

    Iterating a dict gives its keys. To get the matching value you look it up with students[student]. (A list, by contrast, gives you each value directly — and there are no integer positions to loop over in a dict.)

    None: the no-value object

    Sometimes a value is simply missing — a student who hasn't got a patronus yet, say. Python has a built-in object for exactly that: None. It's its own thing, the deliberate absence of a value. You can print it (it shows as the bare word None, no quotes — not an error), and you test for it with is None:

    None is the no-value object. It prints as the bare word None, with no quotes — and no error.

    is None, not == "None"

    None (no quotes) is not the five-letter string "None" — that's a different value. To check for it, write value is None, not value == "None". (A couple more None traps live in the Common mistakes list at the end; this is the one to remember now.)

    A list of dicts

    One key per student only holds one fact. To store more about each student — a house and a patronus — make each entry its own little dict, and collect those dicts in a list. This list of dicts is one of Python's most common data shapes. Draco hasn't got a patronus, so his is None. We loop the list (each item is a dict) and pull three values out of each by key. The sep=", " tells print to put a comma and space between the things we print, instead of its default single space — so each line reads cleanly:

    hogwarts.py final: a list of dicts. Loop the list, index each dict by key. sep=", " separates the three values with a comma. Draco's patronus is None and prints as None.

    Predict: what does the LAST line show for Draco's patronus — quotes, an error, or something else?

    It prints Draco, Slytherin, None — no quotes, no error. None is a real value, so print displays it just fine, as the four letters None (not the string "None", and not a blank). Printing or passing None around never errors — what would error is trying to index or loop over it (e.g. None[0]), because there's nothing inside it.

    Nested loops: a loop inside a loop (Mario)

    A loop body can contain another loop. To draw a grid of bricks (like a wall in Mario) you need rows and columns. Build up to it the same way we built the meows — start with the plain repetition. A column of bricks is just # printed on its own line, three times. Written out by hand, it's the cat's three meows all over again:

    A column, written by hand — three # on three lines. Same starting point as the three-line meow program.

    That's the repetition; now make it a loop, then wrap it in a function so you can ask for any height. print_column(height) is just the loop with 3 swapped for a parameter:

    print_column: one # per line, height times.

    A row is the other direction — bricks across, on one line. No loop needed: multiplying a string repeats it. "#" * 4 builds "####", four copies glued together on one line. (This is a handy shortcut for the special case of repeating one fixed thing — a for loop is still your general tool whenever the body does anything that varies per pass.)

    print_row: width copies on a single line, using string repetition. "?" is a placeholder brick for now — we switch to # shortly.

    print adds a newline by default

    By default, print adds a newline (a line break) at the end of whatever it prints — that's why each print call lands on its own line. You can change that with the end= parameter: print("#", end="") says "add nothing at the end," so the next print continues on the same line. We'll lean on that to build a row of bricks in the square below.

    A square is rows and columns at once: an outer loop for each row, and an inner loop that prints the bricks across that row. The inner print("#", end="") keeps the bricks on one line; then a bare print() after the inner loop adds the newline that ends the row. The comments name each part the way CS50 does:

    Nested loops: outer i = each row, inner j = each brick. end="" keeps a row on one line; the bare print() ends it. print_square(3) draws a 3x3 grid.

    The inner loop runs fully on EVERY outer pass

    For each row the outer loop reaches, the inner loop runs start-to-finish — a whole row of bricks — before the outer loop moves on. The loops do not advance in lockstep (one inner per outer). So the total work is size × size: print_square(3) draws 9 bricks, not 3. Watch the indentation too — the bare print() sits in the outer body (it ends each row), not inside the inner loop. (Curious how a non-square behaves? Change the two range(size) to range(4) and range(2) and predict before you run.)

    Predict: what if you indent the bare print() one more level, putting it inside the inner loop?

    You'd get a newline after every single #, so instead of a 3×3 square you'd print 9 # straight down one column. The bare print() belongs in the outer loop's body — it must run once per row, after the inner loop finishes a full row. Indentation is what decides "end the row" vs. "end every brick": it says which loop a line belongs to.

    Finally, the payoff of writing print_row earlier: a square is just size rows. So print_square can call print_row instead of carrying its own inner loop — the inner end="" loop disappears, replaced by one tidy call. That's the same compose-from-smaller-functions habit behind get_number()/meow()/main() earlier this lecture (here print_row does its work by printing rather than returning). Same 3×3 output, less code, and the outer loop reads like plain English. Now we use # for real:

    Abstraction: print_square reuses print_row, so the row-drawing lives in one place only — no more end="" inner loop to track.

    In the nested-loops print_square(3), how many # characters are printed in total?

    The inner loop runs fully (3 bricks) on every outer pass, and there are 3 outer passes: 3 × 3 = 9. Nested loops multiply, they don't add and don't run in lockstep. Both versions terminate cleanly — neither is an infinite loop.
    Coming from C or Java? (skip unless you know one)

    for i in range(n) replaces the C-style for (int i = 0; i < n; i++) — same 0-to-n-1 sweep, far less punctuation, and Python has no three-part for header. There's also no do/while (a loop that always runs once); for "run the body at least once," use while True with a break as we did above. And Python's list and dict are flexible, growable containers — not fixed-size typed arrays.

    Common mistakes at a glance

    • A while loop needs a line that moves its condition toward False (like i += 1, or i = i - 1 when counting down). Leave it out and it loops forever — the browser cell that shows this is locked from running. Before running any while loop, point to the step.
    • range(n) gives 0, 1, … n-1 — it never includes n. range(3) is 0, 1, 2 (three values); n is the count, not the last value. After a for loop the variable holds the last value used (range(3) leaves it at 2).
    • while True ends only if a break (or return) is reachable. continue does the opposite — it skips the rest of this pass and loops again, so on its own it never leaves. Always ask which input reaches the break.
    • Typing letters into int(input()) raises a ValueError that stops the cell (re-run and enter a number). Each input pop-up pauses the loop, so an input-gated while True can't freeze the tab — press Cancel to stop.
    • A list is reached by position (students[0]); a dict is reached by key (students["Hermione"]). Using a number on a dict — students[0] — raises a KeyError, as does any key that doesn't exist.
    • Looping a dict — for student in students: — hands you the keys, not the values (the opposite of a list, which hands you each value directly). Get the value with students[student].
    • None is the no-value object — not the string "None", and not 0, "", or False. Printing it shows the bare word None (no error); test for it with is None, never == "None". You can't loop over or index None (None[0] raises a TypeError).
    • In nested loops the inner loop runs fully on every outer pass, so the work is size × size, not size. Watch indentation: a print() inside the inner loop ends every brick; one in the outer body ends each row.
    • print() adds a newline by default (which is why each print lands on its own line). print() with no arguments prints a single blank line (used to end a Mario row); end="" turns the trailing newline off so output stays on one line; sep=", " sets what goes between multiple arguments (default is a single space).

    Recap & next step

    You can now make programs repeat. A while loop runs as long as its condition holds, and every while loop needs a step toward the fence or it loops forever — the classic example starts i = 3 / while i != 0: and forgets to lower i (the one box on this page locked from running). The form to reach for is the zero-based one — i = 0 / while i < 3: / i += 1 (+= is shorthand for i = i + 1) — which ends with i sitting exactly on the fence, 3; CS50 arrives at it by refining a broken countdown and a count-up first. A for i in range(n) loop repeats a known number of times, where range(n) is the 0 .. n-1 fence that explains both the off-by-one and why range(len(...)) lines up with a list's indices (use _ when the value is unused); for leaves the variable at the last value used (2 for range(3)). while True plus a reachable break handles \"ask until valid\" — continue loops again, break (or return) leaves on good input (here CS50 keeps positive numbers with if n > 0) — and folding it into a get_number() that returns its value reuses Lecture 0's square and Lecture 1's is_even, with return doing the job of break from inside the loop; int(input(...)) is the read-a-number move from Lecture 1's compare.py and grade.py (bare input() itself goes back to Lecture 0). You met two containers — a list reached by position and a dict reached by key (the same Hermione/Harry/Ron/Draco cast from Lecture 1's match), where looping a list gives values directly but looping a dict gives keys — plus None for a missing value (test with is None), the list-of-dicts shape for richer records (printed with sep=\", \"), and nested loops for a grid (the inner loop runs fully per outer pass, so it's size × size; print(\"#\", end=\"\") then a bare print() builds a row, and print_square later reuses print_row to drop the inner loop).
